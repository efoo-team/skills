# issue-report-dev: エンジニア向け issue 本文形式

起草ワーカー（縮退時は parent）が Phase 6 で使う本文テンプレート。

> **共通規約と書き換え手順は本ファイルにない。** 「対象領域:」定型形式・任意定型行（`関連:` / `現在の挙動に関する観察（事実）:`）・更新履歴・既存 issue の本文書き換え（統合）手順は [`../../issue-report-user/references/issue-format.md`](../../issue-report-user/references/issue-format.md) の共通正本に従う。本ファイルは、そこにある本文テンプレートを**エンジニア向けに差し替える**ものである。

## 1. 共通正本から引き継ぐ規約

- 対象リポジトリの `.github/ISSUE_TEMPLATE/` に該当種類のテンプレートがあればその構成を優先する。その場合も「対象領域:」定型形式と「更新履歴」は必ず含める
- タイトルは「どこで・何が」が一目で分かる形にする（例: `注文履歴画面で並び替え後に一覧が更新されない`）。横断 issue はタイトル先頭に `【横断】` を付ける
- わからなかった項目は削除せず `不明` または `未定` と書いて残す
- 「開発者向け参考情報」セクションの先頭に、共通正本と**同一形式**で対象領域を必ず記載する:

  ```
  対象領域: <画面・機能の言葉での領域> / <ディレクトリ・モジュール等の技術表現>
  ```

  この行は `issue-report-user` / `issue-report-dev` の双方の issue 索引ワーカーが次回以降の照合に使う正本である。形式を変えると照合が推定へフォールバックし、統合先の見逃し（重複 issue）につながる
- 「更新履歴」を本文の最終セクションに置き、登録・統合のたびに1行追記する

## 2. 原因・修正方針・受入条件の書き方

本スキル固有のセクションには、次の規律を必ず適用する。

**原因の仮説**

- 仮説1件につき**根拠を必ず併記**する。根拠は読み取りで確認できた事実（ファイルパス・シンボル名・行範囲・テスト名・ログの該当行・コミット）に限る
- 確認できていない推測は「未検証の点」として**別の小見出しに分離**する。根拠つき仮説と同じ箇条書きに混ぜない
- 原因を特定できなかった場合は `特定できず` と書き、調べた範囲（どこを見て何が否定できたか）を残す。もっともらしい仮説を作らない

**修正方針案**

- 見出しに「案・決定ではない」ことを含める（下記テンプレートの見出しをそのまま使う）
- **複数案を挙げ、それぞれに影響領域とトレードオフを書く**。1案しか無い場合も「他案なし」と分かるように書く
- どの案を採るかを指示しない。設計・実装仕様の確定は着手者と後段の要件定義工程（`/define`）の責務である

**受入条件**

- 検証可能な形（観測できる挙動・テスト観点）で書く。「正しく動くこと」のような判定不能な記述にしない
- 既存テストとの関係（現行仕様を固定しているテストの更新が必要か）が分かっていれば併記する
- 報告者が受入条件を「未定」とした場合は、調査から起こした案を書いたうえで `（未合意。着手前に確認が必要）` と明記する

## 3. 単一ケース用の標準形式

グループに含まれるケースが1件のときに使う。

**不具合用:**

````markdown
## 概要
[1〜2行で問題の要約]

## 現象（事実）
[観測された挙動。エラーメッセージは原文のまま]

## 期待仕様
[本来どうあるべきか。根拠（仕様書・設計意図・型/スキーマ・過去の合意）があれば併記。未定なら「未定」]

## 再現手順
1. [操作・コマンドを順番に]

- 再現環境: [バージョン・OS・ブラウザ・ランタイム等。不明なら「不明」]
- 対象ブランチ / コミット: [例: main@a1b2c3d。不明なら「不明」]
- 再現頻度: [100% / ときどき / 一度だけ]

## ログ・スタックトレース
```
[原文のまま。長い場合は該当箇所を抜粋し、抜粋であることを明記]
```
（無ければ「なし」）

## 原因の仮説
- [仮説]（根拠: `path/to/file.ts` の `symbolName`（L88-104）— [確認できた事実]）

### 未検証の点
- [確認できていない可能性。無ければこの小見出しごと省略]

## 修正方針案（案であり決定ではない）
| 案 | 概要 | 影響領域 | トレードオフ |
|---|---|---|---|
| A | [概要] | [領域] | [副作用・移行コスト・互換性] |
| B | [概要] | [領域] | [同上] |

## 受入条件
- [ ] [観測できる挙動・テスト観点]
- [ ] [既存テストとの関係があれば]

## 影響
[誰が・どの環境で影響を受けているか。本番影響・データ不整合の有無]

## 開発者向け参考情報
対象領域: [画面・機能の言葉での領域] / [技術表現]
関連コミット・PR: [あれば。無ければ省略]

## 更新履歴
- YYYY-MM-DD: 初回登録
````

**要望用:**

```markdown
## 背景・目的
[何のために必要か。現状の何が問題か]

## 期待仕様
[実現後の振る舞い。入出力・境界条件・エラー時の挙動。未定の項目は「未定」]

## 現状の挙動
[いまどうなっているか。関係する既存機能。無関係なら「新規」]

## 既存仕様との関係
[置き換え・変更になる既存挙動、互換性・移行の要否。無ければ「なし」]

## 実装方針案（案であり決定ではない）
| 案 | 概要 | 影響領域 | トレードオフ |
|---|---|---|---|
| A | [概要] | [領域] | [副作用・移行コスト・互換性] |

## 受入条件
- [ ] [観測できる挙動・テスト観点]

## 制約
[互換性・性能・セキュリティ・運用・期限などの制約。無ければ「なし」]

## 開発者向け参考情報
対象領域: [画面・機能の言葉での領域] / [技術表現]
参考実装・関連コミット・PR: [あれば。無ければ省略]

## 更新履歴
- YYYY-MM-DD: 初回登録
```

## 4. 複数ケース用の標準形式

グループに複数ケースが統合されたときに使う。各ケースのセクション構成は、種類（不具合 / 要望）に応じて単一ケース用の該当部分を継承する。

```markdown
## 概要
[この issue に含まれる課題の要約と、1つの issue にまとめている理由
（例: いずれも注文履歴画面のデータ取得層に変更が及ぶため）]

## 対象領域（共通）
[グループ共通の対象領域]

---

## ケース1: [1行タイトル]

### 現象（事実）
### 期待仕様
### 再現手順
### 原因の仮説
### 修正方針案（案であり決定ではない）
### 受入条件

---

## ケース2: [1行タイトル]
...

---

## 開発者向け参考情報
対象領域: [画面・機能の言葉での領域] / [技術表現]
関連コミット・PR: [あれば]

## 更新履歴
- YYYY-MM-DD: 初回登録（ケース1〜2）
```

- 「開発者向け参考情報」はケース横断の共通セクションであるため、共通正本の任意定型行（`関連:` / `現在の挙動に関する観察（事実）:`）を書くときは、どのケースの情報かを `[ケース<番号>]` で明示する
- 原因の仮説・修正方針案・受入条件は**ケースごとのセクションに置く**（ケース横断でまとめない。着手時に対応関係が失われるため）

## 5. 統合（既存 issue への追記）時の扱い

書き換え手順そのものは共通正本（[`../../issue-report-user/references/issue-format.md`](../../issue-report-user/references/issue-format.md)「本文書き換え（統合）手順」）に従う。**既存の記載内容を削除・要約・言い換えしてはならない。** 本スキル固有の注意は次の2点:

- 統合先が `issue-report-user` で作られた issue（技術セクションを持たない形式）である場合、既存本文は一切変更せず、追加ケースの側にだけ原因の仮説・修正方針案・受入条件のセクションを持たせる。既存ケースに対して後から原因仮説を補うことはしない（報告者の記述と調査結果が混ざるため）
- 「開発者向け参考情報」の「対象領域:」は共通正本の手順どおり再計算して更新する（既存の領域は残し、新ケースで加わった領域を追加する）
