# AGENTS.md Composer

プロジェクトルートの `AGENTS.md` を作成・更新する。コードベースの現状把握とユーザーヒアリングを組み合わせ、エージェントがプロジェクトの文脈を理解するために必要な情報を過不足なく記載する。

---

## このスキルを使う場面

- 新規プロジェクトで AGENTS.md を作成する
- 既存の AGENTS.md を更新・拡充する
- プロジェクトの規約や開発フローを明文化したい
- エージェントにプロジェクト固有の制約を伝えたい

## このスキルの対象外

- AGENTS.md 以外のドキュメント作成（README、CONTRIBUTING.md など）
- コーディング規約の実装（linter/formatter 設定ファイルの編集）
- CI/CD パイプラインの構築

---

## 原則

- **事実に基づいて構成する。** コードベースに存在しない規約を捏造しない。不明な点はユーザーに確認する。
- **過剰に書かない。** プロジェクトの規模と成熟度に見合った情報量に留める。起こりうるすべてのケースを事前定義しようとしない。
- **AI が行動を決定できる情報を提供する。** 単なる説明ではなく、エージェントが判断に使える変数とルールを記述する。
- **コードベースの実態と矛盾させない。** すでに存在する設定ファイル（`.eslintrc`, `package.json`, `tsconfig.json` など）や実際のファイル構成と整合させる。

---

## 実行フロー

### Phase 1: 現状把握

#### 1-1. 既存 AGENTS.md の確認

プロジェクトルートに `AGENTS.md` が存在する場合、その内容を分析する。

- すでに記述されているセクションと不足しているセクションを特定する
- 既存の記述とコードベースの実態が一致しているか確認する
- 更新の場合は既存構造を尊重し、破壊しない形で追加・修正する

#### 1-2. コードベース探索

以下の観点でプロジェクトを探索し、AGENTS.md の記述根拠を収集する。

**探索対象:**

| 観点 | 確認手段 | 記述に活かす内容 |
|------|----------|-----------------|
| プロジェクト種別・技術スタック | `package.json`, `Cargo.toml`, `go.mod`, ディレクトリ構造 | プロジェクトの目的・使用技術の特定 |
| ブランチ構成 | `git branch -a`, `git remote show origin` | BASE_BRANCH / PRODUCTION_BRANCH の候補 |
| テスト構造 | テストファイルの命名パターン、テストランナー設定 | テスト方針・E2E ファイル命名規則 |
| コード規約 | `.eslintrc`, `.prettierrc`, `tsconfig.json`, `biome.json` | コーディング規約の記述根拠 |
| CI/CD | `.github/workflows/`, `.gitlab-ci.yml` | ブランチ戦略・テスト自動化の状況 |
| モノレポ構成 | `pnpm-workspace.yaml`, `turbo.json`, `nx.json` | パッケージ境界・ワークスペース構成 |
| 環境変数 | `.env.example`, `.env.template` | 必要な環境変数の列挙 |
| セキュリティ設定 | CORS, CSP, 認証設定ファイル | セキュリティ要件 |

#### 1-3. AGENTS.md env の候補値検出

コードベースから以下の候補値を自動検出する。

**BASE_BRANCH:**
```bash
# 候補検出
git branch -a | grep -E "(develop|main|master|staging)" | head -5
git remote show origin 2>/dev/null | grep "HEAD branch"
```

**PRODUCTION_BRANCH:**
```bash
# 候補検出
git branch -a | grep -E "(main|master|production|release)" | head -5
```

**DEVELOPMENT_PHASE の判定基準:**

| 観測事実 | 推定フェーズ |
|----------|-------------|
| 本番運用中、バグ修正が主、破壊的変更禁止 | 安定運用 |
| 新機能開発と保守が混在 | 両者 |
| 未リリース、MVP 開発中、頻繁な設計変更 | ビルドアンドスクラップ |

ヒューリスティクス:
- `CHANGELOG.md` やリリースタグの有無 → 安定運用の指標
- `package.json` の version が `0.x.x` → ビルドアンドスクラップの指標
- コミット頻度とメッセージパターン → 開発アクティビティの指標

### Phase 2: ヒアリング

Phase 1 で収集した情報を基に、不足している情報を `question` ツールでユーザーに確認する。

#### 質問セット

質問は以下の優先順位で行う。Phase 1 で十分な情報が得られた項目はスキップする。

**基本情報（必須）:**
1. プロジェクトの目的 — このプロジェクトは何を達成するために存在するか（1-2文）
2. 事業的背景 — 誰のための、どんな課題を解決するプロダクトか

**AGENTS.md env（Phase 1 で確定できない場合）:**
3. BASE_BRANCH — PR のマージ先ブランチ（検出候補があれば提示）
4. PRODUCTION_BRANCH — 本番環境の upstream ブランチ（検出候補があれば提示）
5. DEVELOPMENT_PHASE — 開発フェーズ（候補を提示して選択式）

**規約・運用:**
6. コーディング規約 — 既存の linter/formatter 設定以外に守るべき規約はあるか
7. テスト方針 — 単体テスト・E2E テストの実行方法と配置規約
8. Git 操作 — コミットメッセージ規約、ブランチ命名規則
9. セキュリティ要件 — 認証・認可の方式、留意すべき脆弱性対策
10. 特記事項 — 未リリース機能の扱い、既知の技術的負債、チーム固有のルール

### Phase 3: 構成

収集した情報を基に AGENTS.md を構成する。

#### セクション構成

AGENTS.md は以下のセクションで構成する。プロジェクトの実態に合わせて不要なセクションは省略する。

```
1. プロジェクトの目的
2. 事業的背景
3. AGENTS.md env
4. ディレクトリ構成（必要に応じて）
5. 留意すべき事項
6. コーディング規約
7. Git 操作
8. テスト
9. セキュリティ
```

#### 各セクションの記述指針

詳細なテンプレートと記述例は `references/agents-md-sections.md` を参照する。

**1. プロジェクトの目的**
- このプロジェクトの存在意義を 1-2 文で記述する
- 技術スタックの列挙ではない。「何を達成するか」を書く

**2. 事業的背景**
- 誰のための、どんな課題を解決するか
- プロダクトの位置づけやビジネスモデルの要点
- このセクションは必須ではない。事業的文脈がエージェントの判断に影響する場合のみ記載する

**3. AGENTS.md env**

エージェントがプロジェクトの状態をプログラム的に参照できる変数群。以下の形式で記述する。

```markdown
## AGENTS.md env

- `BASE_BRANCH`: <値> — <説明>
- `PRODUCTION_BRANCH`: <値> — <説明>
- `DEVELOPMENT_PHASE`: <値> — <説明>
```

| 変数 | 説明 |
|------|------|
| `BASE_BRANCH` | PR のマージ先ブランチ。原則ここに向けて PR を作成する |
| `PRODUCTION_BRANCH` | 本番環境の upstream ブランチ |
| `DEVELOPMENT_PHASE` | コードの保守的改善の度合い。`安定運用` / `両者` / `ビルドアンドスクラップ` のいずれか |

DEVELOPMENT_PHASE の値:
- **安定運用**: 本番稼働中。破壊的変更は原則禁止。バグ修正と段階的改善が主。
- **両者**: 安定運用と新規開発が混在。新機能は慎重に、既存機能は保守的に。
- **ビルドアンドスクラップ**: スタートアップ・未リリース・技術検証。大胆な変更を許容する。

**4. ディレクトリ構成**

モノレポや複数パッケージ構成の場合、パッケージ境界と責務を簡潔に記述する。
単一パッケージの小規模プロジェクトでは省略可。

**5. 留意すべき事項**

エージェントが作業する上で特に注意すべき制約を列挙する。

- 未リリース機能の扱い（破壊的変更の許容範囲）
- 本番反映済み機能と開発中機能の区別
- 構想を阻害する負債の防止方針
- プロジェクト固有の判断基準

**6. コーディング規約**

- 既存の linter / formatter 設定ファイルを参照するよう指示
- 命名規則（ファイル名、変数名、ディレクトリ名）
- AI スロップ防止のための具体的な指針
- 使用禁止パターン（`any` 型、`@ts-ignore` など）

**7. Git 操作**

- コミットメッセージ規約（Conventional Commits など）
- ブランチ命名規則
- PR の作成フローとマージ条件

**8. テスト**

- テストの追加容易性を確保する方針
- 単体テストの実行情報（コマンド、設定ファイル）
- E2E テストの配置規約（`references/e2e-test-naming.md` を参照）
- テストカバレッジの考え方

**9. セキュリティ**

- 認証・認可の方式
- 環境変数・シークレットの管理方法
- 注意すべきセキュリティ上の制約

### Phase 4: 検証

構成後、以下の観点で検証する。

- [ ] 記述内容がコードベースの実態と矛盾していないか
- [ ] 存在しない規約や未導入のツールを前提にしていないか
- [ ] AGENTS.md env の値が実際のブランチ構成と一致しているか
- [ ] エージェントが判断に使える具体的な情報になっているか（曖昧な表現がないか）
- [ ] プロジェクトの規模に対して情報過多/不足になっていないか

---

## 既存 AGENTS.md の更新時

既存の AGENTS.md を更新する場合は、以下の原則を守る。

- **既存の構造を尊重する。** セクションの順序や見出しレベルを勝手に変更しない
- **不足している情報を補完する。** 既存の記述と矛盾しない形で追加する
- **削除は慎重に。** 古い情報でも意図があって書かれている可能性がある。削除前にユーザーに確認する
- **差分を明示する。** 更新時は何を追加・変更したかをユーザーに報告する

---

## 注意事項

- AGENTS.md に書くべきでないこと: 自動生成される情報、他のファイルと重複する詳細設定、個人の好み
- プロジェクトが小規模な場合、全セクションを埋める必要はない。プロジェクトの目的と最低限の env で十分なこともある
- AGENTS.md env は AI がパースして判断に使うことを想定している。値を正確に記述する
- E2E テストの命名規則は `references/e2e-test-naming.md` を参照し、プロジェクトの実態に合わせて調整する
