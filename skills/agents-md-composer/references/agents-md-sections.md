# AGENTS.md セクションテンプレート

各セクションの詳細な記述指針とテンプレート。

---

## 1. プロジェクトの目的

### テンプレート

```markdown
# プロジェクトの目的

[プロジェクト名] は、[誰のために][何を達成する]ための[アプリケーション/サービス/ライブラリ]である。
```

### 記述指針

- 技術スタックの列挙にしない。「何を達成するか」を書く
- 1-2 文で簡潔に
- エージェントが作業の優先順位を判断できる情報を含める

### 例

```markdown
# プロジェクトの目的

Caremaster は、介護施設の職員が入居者の健康状態とケア記録を一元管理するための Web アプリケーションである。現場の入力負荷を減らし、ケアの質を高めることを目的とする。
```

## 2. 事業的背景

### テンプレート

```markdown
## 事業的背景

- **対象ユーザー**: [誰が使うか]
- **解決する課題**: [どんな問題を解決するか]
- **ビジネスモデル**: [B2B/B2C/SaaS/受託など]
- **競合・差別化**: [あれば]
```

### 記述指針

- 必須セクションではない。事業的文脈がエージェントの判断に影響する場合のみ記載
- 機密情報は含めない

## 3. AGENTS.md env

### テンプレート

```markdown
## AGENTS.md env

エージェントがプロジェクトの状態を参照するための変数。

- `BASE_BRANCH`: `develop` — PR のマージ先ブランチ。原則ここに向けて PR を作成する
- `PRODUCTION_BRANCH`: `main` — 本番環境の upstream ブランチ
- `DEVELOPMENT_PHASE`: `両者` — コードの保守的改善の度合い
```

### DEVELOPMENT_PHASE の値と意味

| 値 | 意味 | 典型的なプロジェクト |
|----|------|---------------------|
| `安定運用` | 本番稼働中。破壊的変更は原則禁止。バグ修正と段階的改善が主 | 長期運用中の既存プロダクト |
| `両者` | 安定運用と新規開発が混在。新機能は慎重に、既存機能は保守的に | アクティブに機能追加中のプロダクト |
| `ビルドアンドスクラップ` | スタートアップ・未リリース・技術検証。大胆な変更を許容する | 新規開発、PoC、技術検証 |

## 4. ディレクトリ構成

### テンプレート

````markdown
## ディレクトリ構成

```
project-root/
├── src/           # アプリケーションソースコード
│   ├── api/       # API エンドポイントハンドラ
│   ├── domain/    # ドメインロジック
│   └── infra/     # インフラ層（DB、外部API）
├── tests/         # テストコード
└── docs/          # ドキュメント
```
````

### 記述指針

- モノレポの場合はパッケージ境界と責務を記述する
- 単一パッケージの小規模プロジェクトでは省略可
- コード生成物やビルド成果物のディレクトリは省略

## 5. 留意すべき事項

### テンプレート

```markdown
## 留意すべき事項

- [重要な制約や方針]
- [未リリース機能の扱い]
- [本番反映済み機能と開発中機能の区別]
```

### よくある記述項目

```markdown
## 留意すべき事項

- 未リリース機能のコードは `feature/` ブランチ上にのみ存在する。本番ブランチには含まれていないことを前提に、破壊的変更を許容する
- 本番に反映済みの機能に対する破壊的変更は原則禁止。非推奨化→移行期間→削除の手順を踏む
- 既存の設計意図を理解せずに「とりあえず動く」修正を積み重ねると、構想を阻害する負債になる。変更前に設計意図を確認する
- `src/legacy/` 配下のコードは移行中の旧実装。新規機能はこのディレクトリに追加しない
```

## 6. コーディング規約

### テンプレート

```markdown
## コーディング規約

### 設定ファイル

- ESLint: `.eslintrc.js`
- Prettier: `.prettierrc`
- TypeScript: `tsconfig.json`

コードのスタイルと品質は上記設定ファイルに従う。設定ファイルと矛盾するコードを生成しない。

### 命名規則

- ファイル名: [kebab-case / PascalCase / camelCase]
- 変数名: [camelCase]
- 型・インターフェース名: [PascalCase]
- ディレクトリ名: [kebab-case]

### AI スロップ防止

- 型安全性を損なうコードを生成しない（`as any`, `@ts-ignore`, `@ts-expect-error` の不使用）
- 空の catch ブロックを書かない
- 到達不能コードを生成しない
- 未使用の import や変数を残さない
- コードの重複を避け、既存の抽象化を理解してから変更する
```

## 7. Git 操作

### テンプレート

````markdown
## Git 操作

### コミットメッセージ

[Conventional Commits / 独自規約] に従う。

```
type(scope): description
```

| type | 用途 |
|------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `refactor` | リファクタリング |
| `docs` | ドキュメント |
| `chore` | ビルド・CI・依存関係 |

### ブランチ戦略

- ブランチ命名: `feature/<概要>`, `fix/<概要>`, `chore/<概要>`
- PR のマージ先: `BASE_BRANCH`（AGENTS.md env 参照）
- PR マージ条件: CI パス + 1 名以上のレビュー承認

### PR 作成

- PR 作成には `gh pr create` を使用する
- 本文は標準入力を使用し、`--body` 形式は使わない
````

## 8. テスト

### テンプレート

````markdown
## テスト

### テストの方針

- テストの追加容易性を確保する。テストが書きにくいコードは設計に問題がある可能性を疑う
- 新機能には単体テストを必須とする
- バグ修正には回帰テストを追加する

### 単体テスト

```bash
# テスト実行
npm test
# または
pnpm test
```

- テストフレームワーク: [Jest / Vitest / Mocha / なし]
- テストファイルの配置: [対象ファイルの隣接 / `__tests__/` ディレクトリ]

### E2E テスト

E2E テストファイルの命名規則は以下の通り。

```txt
<e2e-root>/<stable-grouping-path>/<behavior-contract>.spec.ts
```

- `<e2e-root>`: E2E テストのルートディレクトリ（例: `e2e/`）
- `<stable-grouping-path>`: プロジェクト内で長期的に変更されにくい分類軸（domain, feature, route, journey, user-role など）
- `<behavior-contract>`: 検証対象の振る舞い・仕様上の契約を kebab-case で表す

E2E 以外の spec と同一階層で混在する場合のみ `.e2e.spec.ts` を使用する。

browser、device、environment、priority、実行順はファイル名に含めない。これらはテストランナーの設定側で管理する。

```bash
# E2E テスト実行
npx playwright test
```

```txt
# ファイル構成例
e2e/workspaces/line-account-settings/reject-invalid-line-connection-config.spec.ts
e2e/workspaces/line-account-settings/create-line-connection-url.spec.ts
e2e/journeys/onboarding/complete-initial-setup.spec.ts
```

### テストカバレッジ

[カバレッジ目標や計測方法があれば]
````

## 9. セキュリティ

### テンプレート

```markdown
## セキュリティ

### 認証・認可

- 認証方式: [JWT / Session / OAuth 2.0 / API Key]
- 認可モデル: [RBAC / ABAC / 独自]

### 環境変数・シークレット

- 環境変数は `.env.example` に定義されている
- シークレット（API キー、トークン、パスワード）は環境変数で管理し、コードベースにコミットしない
- `.env` ファイルは `.gitignore` に含まれている

### 注意事項

- ユーザー入力は常にバリデーションとサニタイズを行う
- SQL インジェクション対策: プリペアドステートメントまたは ORM の安全なクエリビルダーを使用
- XSS 対策: ユーザー入力を HTML に埋め込む際はエスケープする
- CSRF 対策: [トークン方式 / SameSite Cookie / 未対策]
- 依存関係の脆弱性は定期的に監査する
```
