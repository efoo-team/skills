# 事例集（case-studies）

配置・統合・開示の worked example。形式は「状況 → 選択肢 → 判断 → 適用した基準」。新しい設計判断で基準の適用に迷いが生じたら、判断の確定後にここへ追記する。事例が溜まって一般化できるものは SKILL.md の基準へ昇格する。

## 事例1: 申請系アクションの入口統合

- **状況**: カレンダー画面に申請系のボタンが種別ごとに並び、画面の情報量が増えてユーザーが混乱していた。
- **選択肢**: A) 種別ごとのボタンを維持する。B) 単一の「申請」入口に統合し、種別の選択を入口通過後（モーダル内のタブ等）に移す。
- **判断**: B。ユーザーの最初の一言はどの種別でも「申請したい」で同じ（動機の粒度が種別より粗い）ため、第一画面には「申請できる」ことだけを動機と同じ粒度で示し、種別の選択は開示層で行わせる。頻用者向けに、最頻種別のデフォルト選択と前回選択の記憶で効率を担保する。
- **適用基準**: 入口の統合と段階的開示（統合判定＝最初の一言）、動機の粒度と同じ粒度の入口ラベル。

## 事例2: 動線内でのテンプレート作成

- **状況**: 繰り返し使う入力パターンをテンプレート化する機能を、管理メニュー配下の専用画面に置くか、入力作業の画面内に置くかが論点になった。
- **選択肢**: A) 管理メニューに専用のテンプレート管理画面を置く。B) 入力動線の中に「この内容をテンプレートとして保存」を置く。
- **判断**: B。テンプレートを作りたい動機は入力作業の最中にしか発生しない。将来を楽にする投資行動は遷移コストに弱いため、動線内で完結させ、必要の瞬間に視界へ入る pull 型で気づかせる。一覧・削除などの管理面は従来どおり管理画面に置いてよい（作成の入口だけを動線内に置く）。
- **適用基準**: 動線内完結と投資、動機起点の配置。

## 事例3: 外部連携設定の単一入口

- **状況**: 外部サービス連携の設定ボタンを、連携対象の帰属単位（組織・拠点・個人）ごとの管理画面へ分散配置する案があった。
- **選択肢**: A) 帰属単位ごとの画面にそれぞれ連携ボタンを置く。B) 単一の連携入口に統合し、帰属先の選択を入口通過後に行わせる。
- **判断**: B。分散配置は「その画面の単位でしか連携できない」という機能可用性の誤解を生む。帰属先はデータモデル上の区分であって動機の区分ではないため、配置を帰属先で割らない。入口は動機が発生する画面に1つ置き、開示層で帰属先を選ばせる。
- **適用基準**: 帰属先と配置場所の区別、配置＝機能可用性の宣言、入口の統合と段階的開示。
