## 1. 作業ディレクトリと案のファイル

検討の資料は、プロジェクトの root ディレクトリの `logo-work/` に置く。

```
logo-work/
├── refs/                  # 参考ロゴの画像（比較専用）
├── round-1/ round-2/ …    # ラウンドごとの案のディレクトリ
├── finalists/             # 最終候補（案のディレクトリと同じファイル構成）
├── out/                   # 生成した画像（ホーム画面の確認画像、選定用の比較画像）
└── LOG.md                 # ラウンドの記録
```

案のディレクトリには、スクリプトの入力仕様（`scripts/README.md`）に合わせて、次のファイルを置く。

| ファイル | 内容 |
|---|---|
| `<ID>.icon.svg` | 必須。アプリアイコン。`viewBox="0 0 1024 1024"`、角丸なしの四隅まで塗った正方形。アイコン背景は `id="background"`、シンボルマークは `<g id="symbol">` |
| `<ID>.symbol.svg` / `<ID>.symbol-dark.svg` | シンボルマークだけ（明るい背景用・暗い背景用） |
| `<ID>.favicon.svg` | favicon 用に簡略にした版 |
| `<ID>.lockup.svg` / `<ID>.lockup-dark.svg` | ロックアップ（明るい背景用・暗い背景用） |
| `designs.json` | 案ごとの `id`・`name`・`idea`（着想 1〜2 文）・`ideaType`（発想の種類。動作の比喩・感情・文字由来・純粋な抽象・文化のいずれか）・`palette`・`logotypeFont` |

案の ID は、英数字・日本語・`.` `_` `-` だけにする（出力のファイル名に使うため）。アプリアイコンに角丸は付けない。丸めはホーム画面やストアが後から行うので、`icon.svg` は四隅まで塗る。

## 2. 参考ロゴの集め方

参考ロゴ（方針の表の参考ブランドと競合ロゴ）の画像は、スクリプトが読む `logo-work/refs/` に置く。集める時期は、方針の表を利用者に示した後、第 1 ラウンドのホーム画面の確認画像を生成する前である。低コストモデルに任せてよい。

集め先は、各社の公式のブランドのページ（プレスキット、ブランドガイドライン）と、ストアの公開ページ（アプリのアイコン）である。非公式の転載サイトからは集めない。アプリのアイコンは、取得できる最大の正方形を、512 px 以上の PNG で保存する。シンボルマークだけの SVG があれば、`<slug>.svg` としても保存する。ファイル名は `<slug>.png` とし、`<slug>` は小文字・ハイフン区切りのブランド名にする（例: `linear.png`）。表示名を変えたいときは、`refs/manifest.json` に `{"linear": "Linear"}` の形で書く。

参考ロゴは、比較にだけ使う。報告書や公開物に載せない。商標は各社のものである。

集められないブランドは、代わりのロゴを作らず、方針の表の参考ロゴから外し、その旨を利用者に伝える。集まった数が、参考ブランドで 3 件未満、または競合ロゴで 2 件未満なら、集め直す。それでも足りなければ、足りないことを報告に書く。

競合ロゴは、サービスの想定ユーザーが比較検討する代替サービスと、ストアや検索結果の同じ一覧に表示される類似サービスから、3〜5 件を選ぶ。シンボルマークだけの SVG は、類似検索の追加の比較対象（`--extra-set`）にも使える。

## 3. ラウンドごとの手順

1. **第 1 ラウンドは、意味の軸と形の種類の軸を掛け合わせて、10 案以上を描く。** 方針の表の「第 1 ラウンドの意味の軸」と「形の種類」を掛け合わせる。どの案も、細い線の UI アイコンとしてではなく、面と比率と色を丁寧に設計したブランドのシンボルマークとして描く（`svg-craft.md` §1）。
2. **描く前に、案ごとの着想を 1 文で書く。** 1 文で言えない案は描かない。描いた後に着想を付けると、着想の薄い案が残る。
3. **描いたら、ホーム画面の確認画像を生成し、目で見て評価する。** 毎ラウンド、`home-screen.mjs` で、案を参考ロゴと同じ大きさで並べたホーム画面のモックアップと、サイズ別の並べ比べを生成する。方針の表の「確認する表示場面」（ストア・ヘッダー・タブなど）は、`candidate-comparison.mjs --scenes <表示場面>` で、ラウンドの途中から確認してよい。画像を開いて、自分の目で見る。点数の表を判断の代わりにしない。
4. **第 2 ラウンド以降は、着想と形が互いに異なる 4 案以上を、方針の表の内訳に従って最後まで並行して残す。** 1 案の細部だけを詰めるラウンドにしない。案を不採用にしたら、内訳に従って、別の着想の案を追加する。
5. **ラウンドごとに、何を追加し、何を不採用にしたかを、理由とともに記録する。** 不採用の理由は、何に見えるかで書く（§5）。
6. **ラウンドの途中で、最終候補の内訳を点検する。** 方針の表からのずれを、ホーム画面の確認画像を見て確かめる（§9）。
7. **3 ラウンド以上回す。** 最終候補が、着想と形が互いに異なる 4〜6 案になり、方針の表の内訳に合い、評価の観点（§6）を満たす水準になったら、工程 4 に進む。5 ラウンド回しても、評価の観点を満たす水準に届かないときは、届いていない観点と原因を利用者に報告して止まる。

## 4. 描くサブエージェントへの指示文のテンプレート

描く作業を委譲するときは、次の内容を 1 つの文面にまとめ、最初に一括で渡す。要件を分割して渡すと、精度が下がる。

```markdown
## 目的
<サービス名>（<何をするサービスか 1 文>）のロゴの案を描く。第 N ラウンド。

## 方針の表
<方針の表をそのまま貼る>

## 描くもの
- 方針の表の最終候補の内訳に従い、発想の種類ごとに案を描く: <発想の種類: 案数> を、種類の数だけ並べる。
- 第 1 ラウンドは、意味の軸（<軸の一覧>）と形の種類（<種類の一覧>）の組み合わせから <10 案以上> を描き、各案に発想の種類を 1 つ付ける。第 2 ラウンド以降は、残した発想の種類のそれぞれについて、<k> 案以上を並行して描く。
- 描く前に、案ごとに着想を 1 文で書く。1 文で言えない案は描かない。
- 置き場所は `logo-work/round-<N>/`。ID は英数字・日本語・`.` `_` `-` だけにする（例: `D1a`）。
- 案ごとに、`<ID>.icon.svg`、`<ID>.symbol.svg`、`<ID>.symbol-dark.svg` を作る。`designs.json` に、案ごとの `id`・`name`・`idea`・`ideaType` を書く。

## 描き方
- 細い線の UI アイコンとしてではなく、面と比率と色を丁寧に設計したブランドのシンボルマークとして描く。
- `icon.svg` は `viewBox="0 0 1024 1024"`、角丸なしの四隅まで塗った正方形にする。アイコン背景は `id="background"`、シンボルマークは `<g id="symbol">`。
- 参考ロゴの形は写さない。
- <`references/svg-craft.md` §1 の要点（連続曲率の曲線、折れ線を最終品質にしないこと、既製の字形をそのまま使わないこと、光学的な中心）を貼る。サブエージェントは references を読めない前提で書く>

## 評価の観点（第一は、アイコンとしての美しさと洗練）
<§6 の評価の観点をそのまま貼る>

## 避けるもの
<§7 の一覧をそのまま貼る>

## 確認の仕方
- `home-screen.mjs` で、案を参考ロゴの隣に置いた画像を生成し、自分の目で見て直す。点数の表を判断の代わりにしない。
- 描いたら、各案が他の何に見えるか（誤認）を具体名で挙げる（§8）。

## 返すもの
- 案のディレクトリの場所、案ごとの着想（1 文）、不採用にした案とその理由（何に見えるか）、ホーム画面の確認画像のパス。
```

## 5. ラウンドの記録のテンプレート

`logo-work/LOG.md` に、ラウンドごとに次の形で書く。不採用の理由は、「水滴に見える」「ベン図に見える」のように、何に見えるかで書く。「平凡」「弱い」のような抽象的な語では、次のラウンドの描き方に使えない。

```markdown
## 第 N ラウンド

- 描いた発想の種類と案数: <発想の種類: 案数>
- 追加したもの: <案・発想の種類・修正> — 理由: <…>
- 不採用にしたもの: <ID> — <何に見えるか> / <ID> — <何に見えるか>
- 採用して残したもの: <ID と着想 1 文>
- 最終候補の内訳の点検: <方針の表との差と、直し方>
```

## 6. 評価の観点

評価の第一の観点は、アプリアイコンとしての美しさと洗練である。着想・覚えやすさ・独自性より上に置く。着想がよくても、美しくない案は残さない。ホーム画面の確認画像と選定用の比較画像を見るたびに、次の 6 点を目で確かめる。

1. 輪郭が一目で美しいか。
2. 曲線が滑らかか。既製の字形や折れ線をそのまま使っていないか。
3. 光学補正（optical alignment）をしているか。
4. アイコン背景の中で、シンボルマークの大きさと余白が釣り合っているか。
5. 色の選び方に理由があるか。光や奥行きを使うなら控えめか。
6. ホーム画面で参考ロゴの隣に置いたとき、実行者自身がそのアプリアイコンを使いたいと思えるか。

判断は、画像を自分の目で見て行う。着想を 1 文で言えない案は残さない。着想の重みは、方針の表の「着想の書き方と重み」に従う。

小さいサイズ（32 px と 16 px）で表示したときの読みやすさと、他社の既存のロゴと似ていないことは、第二以下の条件である。小さいサイズで崩れる案は、favicon 用に簡略にした版（`<ID>.favicon.svg`）を別に作ってよい。

## 7. 避けるもの

次のものは避ける。

- AI-slop のパターン: きらめき、光沢のある 3D、意味のない流線、紫から青へのグラデーションで全面を塗った形、ロケット・雲・紙飛行機・矢印、角丸の正方形に頭文字を置いた形。
- 有名なロゴの形と配色（他社の商標の形や、他社のロゴに紛らわしい配色を含む）。
- 具体的な物への偏り。文化や業種の具体的な物（道具・紋・食べ物）は、その業種のロゴに誤認されやすい（§8、§9）。

## 8. 誤認の確認

誤認とは、ロゴが意図と別の物に見えることである。案ごとに、次を具体名で挙げて確かめ、記録する。

- 形の似ている身近な物（サービスの題材と無関係なものも含める。例: 水滴、ベン図、勲章、電波の棒、レンズ、地球儀）。
- 他社のアイコン、色の組み合わせが連想させるブランド。
- 特定の業種のロゴ（飲食店・小売店・宿泊施設など）。サービス自身の題材や出自に近い業種（たとえば料理のサービスなら、飲食店）は、とくに誤認されやすい。方針の表の誤認の確認の強さに応じて、全案で確認する。
- 文化ごとに特別な意味を持つ色の組み合わせ（例: 黒と白は弔事）。出自の要素を使う案で確認する。
- 小さな要素の有無で見え方が変わる案。要素を外した版も描いて比べる。

## 9. 最終候補の内訳の中間点検

ラウンドの途中（ホーム画面の確認画像を生成した時点）で、最終候補の内訳が方針の表からずれていないかを、ホーム画面の確認画像を見て確かめる。ずれの典型は、具体的な物への偏りである。出自の具体的な物（その文化の道具・紋・食べ物など）に案が集まると、その業種のロゴに誤認される。早い時点で偏りに気づくほど、直す手間が小さい。

点検は、次の順で行う。

1. ホーム画面の確認画像の案を、発想の種類（動作の比喩・感情・文字由来・純粋な抽象・文化）に振り分ける。
2. 発想の種類ごとの案数を、方針の表の内訳と比べる。出自の要素を使う案が上限を超えていないか、純粋な抽象が減りすぎていないかを見る。
3. ずれていたら、描くサブエージェントに、理由と割り振り直した案数を指定して、そのラウンドのうちに描き直させる。

この点検は、描いたサブエージェントの自己申告に任せず、実行者がホーム画面の確認画像を見て行う。

## 10. 他社の既存のロゴとの類似の確認

最終候補の全案について行う。

1. `scripts/similar/similar.mjs <案のディレクトリ> --rot --out <dir>` で、公開されているアイコン集（simple-icons・lucide・tabler・Material Symbols）と照合する。`--rot` を付けると、回転・反転の 8 通りのうち最も高い類似度を採る。競合ロゴの SVG があれば、`--extra-set <dir>` で比較対象のアイコン集に追加する。
2. Web で、同じモチーフの他社の既存のロゴを集め、同じ大きさで並べた画像を生成する（集め方は §2 と同じ。比較専用）。
3. 類似度は、最初のふるい分けに使う手がかりであり、判断の代わりにしない。類似度が見るのは、シンボルマークの輪郭（silhouette）の似かたである。内側の構造（面の分割や、穴の中の形）の違いは、類似度に出にくい。上位に出たロゴは、目で見て、本当に似ているかを確かめる。輪郭と内側の構造がともに似ている案は、最終候補から外す。輪郭だけが似ている案は、形を修正して残してよい。文字由来の案は、同じ頭文字の他社の既存のロゴが上位に出やすいので、とくに注意する。
4. 画像検索と商標の図形検索は、この skill のスクリプトではできない。この限界を、利用者への報告に書く。公開前の商標の確認は、利用者が行う（必要なら、利用者が法務担当者に依頼する）。

## 11. 最終候補と選定用の比較画像

最終候補は 4〜6 案とし、すべて着想と形が互いに異なる案にする。色違いや太さ違いは並べない。発想の種類の内訳は方針の表に従い、同じ発想の種類の案が複数あってよい。案ごとにロックアップを作る。ロゴタイプの書体は、OFL などのライセンスが許すものを選び、outline の path にして、書体名とライセンスを `designs.json` に記録する（`scripts/text2path/`、`svg-craft.md` §4）。

選定用の比較画像は、`candidate-comparison.mjs` で生成する。表示場面ごとの行に全案を並べた 1 枚と、案ごとの 1 枚を生成し、各案の着想（1〜2 文）、類似の確認結果、懸念、推奨を添える。

選定案を決めるのは利用者である。選定用の比較画像を利用者に示して、選んでもらう。選択肢には「どの案も採らず、もう 1 ラウンド」を入れる。実行者は推奨を書いてよいが、利用者が推奨と別の案を選んだときは、選定案に従う。「もう 1 ラウンド」が選ばれたら、利用者が挙げた理由を方針の表に反映して、1 ラウンドだけ回す。
