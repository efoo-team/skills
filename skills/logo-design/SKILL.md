# logo-design

サービスのロゴを、毎回同じ質で作る手順である。完了まで数時間かかり、利用者に質問し、サブエージェントも動かす。

過去の失敗は 2 つある。1 つ目は、評価の第一を美しさ以外（小さいサイズで読めること、他社の既存のロゴと似ていないこと）に置いたため、シンボルマークが地味になり、最後に文字だけの案が残ったことである。2 つ目は、1 ラウンドで案を決め、最終候補を利用者に見せず、選んでもらわなかったことである。この skill は、方針を先に決め、着想と形が互いに異なる案を並行して検討し、利用者に選んでもらう順序で、この 2 つを防ぐ。

## 用語

| 用語 | 意味 |
|---|---|
| ロゴ | シンボルマークとロゴタイプを合わせた全体 |
| シンボルマーク | ロゴの図形の部分 |
| ロゴタイプ | ロゴの文字の部分。サービス名を書体で書いたもの |
| ロックアップ | シンボルマークとロゴタイプを並べた組み合わせ |
| アプリアイコン | アイコン背景の上にシンボルマークを置いた、四隅まで塗った正方形の画像。角丸は付けない |
| アイコン背景 | アプリアイコンで、シンボルマークの後ろに全面に塗る正方形 |
| 案 | 1 つのロゴのデザイン案 |
| 最終候補 | 利用者に選んでもらうために最後まで残す 4〜6 案 |
| ラウンド | 案を描いて評価する 1 回の繰り返し |
| 誤認 | 意図と別の物（特定の業種のロゴ、他社のロゴ、身近な物）にロゴが見えること |
| 選定案 | 利用者が最終候補から選んだ 1 案 |
| 発想の種類 | 案の発想の分類。動作の比喩・感情・文字由来・純粋な抽象・文化の 5 種 |
| 着想 | 案がなぜその形かを説明する 1〜2 文 |
| 参考ロゴ | 比較のために並べる他社ブランドのロゴ（アプリアイコンの画像）。参考ブランドのロゴと、競合サービスのロゴ（競合ロゴ）から成る |
| ホーム画面の確認画像 | `home-screen.mjs` が生成する、案を参考ロゴの隣に置いたホーム画面のモックアップと、サイズ別の並べ比べ |
| 選定用の比較画像 | `candidate-comparison.mjs` が生成する、表示場面ごとに全案を並べた 1 枚と、案ごとの 1 枚 |
| 画面の背景 | ロゴを置く先の画面の背景（明るい背景・暗い背景）。アイコン背景とは別 |
| 高性能モデル・低コストモデル | サブエージェントに指定するモデルの区分。Claude Code では、高性能モデルが opus、低コストモデルが sonnet |
| 出自の要素 | サービスの出自（国・地域・文化・創業の背景）に由来するモチーフ・色・形 |
| 面 | シンボルマークを構成する、1 色で塗った領域 |
| 表示場面 | ロゴが表示される画面と大きさ（ホーム画面、ブラウザのタブ、ストアなど） |
| 連携先 | ロゴやアプリアイコンを提出する外部サービス、またはアプリを接続する外部サービス（ストア、OAuth の提供元など） |
| 最終候補の内訳 | 最終候補の 4〜6 案について、発想の種類ごとの案数を決めた計画。ラウンドの途中の案も、この内訳に沿って点検する |
| 制作品質の修正 | 選定案の見た目を変えずに、favicon の簡略版・ピクセル整列・輪郭・余白・曲線化などを直すこと（工程 5 の前半） |
| 意味の軸・形の種類の軸 | 第 1 ラウンドで掛け合わせる 2 つの軸。意味の軸は着想の元になる意味の候補（動作・感情・文字・抽象的な形）、形の種類の軸は図形の作り方の候補（幾何学的な形・有機的な曲線・手描きの線）。軸の中の選択肢を項目と呼ぶ |
| 実行者 | この skill に従って作業するエージェント |

## 読む順序

`references/rounds-and-evaluation.md` は、§1 を工程 0、§2 を工程 2 の後、§3 以降を工程 3〜4 で読む。`references/policy-table.md` は工程 2 で読む。`references/svg-craft.md` は、案を描くとき（§1）、工程 4 のロックアップの制作（§4）、工程 5（§2・§3）で読む。

## 工程一覧

実行者は、次のチェックリストを自分の応答に貼って進捗を管理する。

- [ ] 工程 0: 事実の収集
- [ ] 工程 1: 3 つの問い（回答が揃うまで次に進まない）
- [ ] 工程 2: 方針の表の提示
- [ ] 工程 3: 検討（3 ラウンド以上）
- [ ] 工程 4: 最終候補と選定用の比較画像（利用者が選ぶまで次に進まない）
- [ ] 工程 5: 制作品質の修正と書き出し

### 工程 0: 事実の収集

次の事実は問いにしない。会話・リポジトリ・既存のサイトから先に読み取り、どうしても分からないものだけを短く尋ねる。

- サービスの名前と、何をするサービスか
- ロゴを表示する画面と大きさ（ストア、同意画面、サイトのヘッダー、ブラウザのタブ、ホーム画面など）。これを表示場面と呼ぶ
- 既存の色の制約と、製品の画面が状態の表示に使っている色
- 連携先（ストアを含む）の審査の規則。要件を拡大解釈も縮小解釈もしないために、原文で読む。原文は、連携先の公式ドキュメントから取得するか、利用者から受け取る。原文が入手できず、他者による要約しか無いときは、その旨を「要確認」として方針の表に残す

初回だけ、`bash <skill のディレクトリ>/scripts/setup.sh` を実行する。依存パッケージ・書体・chromium を `LOGO_DESIGN_HOME`（既定は `~/.cache/logo-design`）に用意するスクリプトであり、読むものではなく実行するものである。次に、`references/rounds-and-evaluation.md` §1 に従って作業ディレクトリ `logo-work/` を作る。git のリポジトリの中なら、git の対象外にする。

### 工程 1: 3 つの問い

次の 3 問を、利用者のハーネスが持つ構造化された質問の機能（Claude Code の AskUserQuestion など）で、1 回にまとめて出す。各問いに選択肢と説明を付け、自由記述も受ける。この 3 問は、回答によって後の方針の多くが決まるよう選んである。3 問の数と中身は、状況に合わせて増減しない。

**問い 1（見出し: ブランドの系統）**「このアプリアイコンがホーム画面やブラウザのタブに並んだとき、隣にあって自然なのは、どの系統のブランドですか？」

| 選択肢 | 説明 |
|---|---|
| 静かな精密さ | Linear・Stripe・Vercel・Raycast のように、無彩色を基調にして、精度の高さで見せる |
| 親しみやすさと温かみ | Notion・Headspace・Duolingo・Slack のように、手で作ったような質感と温かみがある |
| 上質さと余白 | Aesop・無印良品・Apple のように、余白の広さと抑制で上質さを出す |
| 大胆な表現 | Figma・Spotify・Arc・Discord のように、強い形と色で主張する |
| 自由記述 | ブランド名を挙げる |

**問い 2（見出し: 最初に伝える）**「ロゴを見た人に、最初に受け取ってほしいのは何ですか？」

| 選択肢 | 説明 |
|---|---|
| サービスが何をするか | 動作の比喩（束ねる・送り出す・開く など） |
| 使うとどう感じるか | 安心・軽さ・速さ などの感情 |
| 名前そのもの | 文字や頭文字を丁寧に設計したシンボルマーク |
| 意味より一目で覚えられる形 | 意味を持たない抽象的な形 |

**問い 3（見出し: 出自の要素）**「サービスの出自（国・地域・文化・創業の背景）を、ロゴにどこまで表しますか？」

| 選択肢 | 説明 |
|---|---|
| 表さない | どの国でも同じに読める形 |
| 抽象化して控えめに | 比率・面の分割・色に反映し、具体的な物は描かない |
| はっきり使う | その出自の要素（モチーフ・色・形）を明確に使う |

工程 0 で分からなかった事実が 1 つだけ残っているときは、その確認を 4 問目として同じ呼び出しに入れる。複数残っているときは、先に会話で短く尋ねる。利用者がまだ答えていない問いを推測で埋めて進まない。3 問の回答が揃うまで、工程 2 に進まない。

### 工程 2: 方針の表

`references/policy-table.md` の対応表を引いて、方針の表を作り、利用者に示す。方針の表は、参考ロゴ・形の種類・配色の方針・最終候補の内訳・避けるもの・確認する表示場面を含む。示したら、そのまま工程 3 に入る。利用者が表を直したら、直した表を以降の唯一の方針にする。ラウンドの途中で直されたときは、次のラウンドから反映し、すでに描いた案は、直した方針に照らして採用か不採用かを判定し直す。

方針の表の参考ロゴの画像は、表を示したあと、第 1 ラウンドのホーム画面の確認画像を生成する前に集める。集め方は `references/rounds-and-evaluation.md` §2 に書いた。低コストモデルに任せてよい。

### 工程 3: 検討

詳細は `references/rounds-and-evaluation.md` に書いた。要点は次のとおりである。

1. **3 ラウンド以上**回す。第 1 ラウンドでは、意味の軸と形の種類の軸を掛け合わせて、**10 案以上**を描く。どの案も、細い線の UI アイコンとしてではなく、面と比率と色を丁寧に設計したブランドのシンボルマークとして描く。
2. 第 2 ラウンド以降は、**着想と形が互いに異なる 4 案以上を、方針の表の内訳に従って最後まで並行**して残す。1 案の細部だけを詰めるラウンドにしない。
3. ラウンドごとに、何を追加し、何を不採用にしたかを、理由とともに `logo-work/LOG.md` に記録する。不採用の理由は、「蓮に見える」「ベン図に見える」のように、**何に見えるか**で書く。
4. ラウンドの途中で、最終候補の内訳が方針の表からずれていないかを、実行者がホーム画面の確認画像を見て確かめる。文化や業種の具体的な物に偏ると、その業種のロゴに誤認される。
5. ホーム画面の確認画像を生成するたびに、画像を自分の目で見て評価する（「評価の観点」の節）。画像には、案が参考ロゴと同じ大きさで並ぶ。
6. 5 ラウンド回しても、評価の観点（`references/rounds-and-evaluation.md` §6）を満たす水準に届かないときは、届いていない観点と原因を利用者に報告して止まる。

### 工程 4: 最終候補と選定用の比較画像

最終候補は **4〜6 案、すべて着想と形が互いに異なる案**にする。色違いや太さ違いは並べない。発想の種類の内訳は方針の表に従い、同じ発想の種類の案が複数あってよい。案ごとにロックアップも作り、他社の既存のロゴとの類似の確認（`references/rounds-and-evaluation.md` §10）を全案で行う。

選定用の比較画像（`candidate-comparison.mjs`）を生成して、利用者に示す。この画像は、表示場面ごとの行に全案を並べた 1 枚と、案ごとの 1 枚から成り、各案の着想（1〜2 文）、類似の確認結果、懸念、推奨を添える。**選定案を決めるのは利用者である。** 選択肢には「どの案も採らず、もう 1 ラウンド」を入れる。利用者が選ぶまで、工程 5 に進まない。

### 工程 5: 制作品質の修正と書き出し

選定案の見た目を変えずに、制作品質だけを上げる。修正する項目と書き出す項目は `references/svg-craft.md` に書いた。直した箇所は、修正前後を並べた画像（`before-after.mjs`）で残す。書き出すのは、シンボルマークの SVG（明るい背景用・暗い背景用）、アプリアイコン（SVG と、必要な大きさの PNG。四隅まで塗った正方形）、favicon、ロックアップである。

## 評価の観点

評価の第一の観点は、アプリアイコンとしての美しさと洗練である。着想・覚えやすさ・独自性より上に置く。ホーム画面の確認画像と選定用の比較画像を見るたびに、次の 6 点を目で確かめる。

- 輪郭が一目で美しいか。
- 曲線が滑らかか。既製の字形や折れ線をそのまま使っていないか。
- 光学補正（optical alignment）をしているか。
- アイコン背景の中で、シンボルマークの大きさと余白が釣り合っているか。
- 色の選び方に理由があるか。光や奥行きを使うなら控えめか。
- ホーム画面で参考ロゴの隣に置いたとき、実行者自身がそのアプリアイコンを使いたいと思えるか。

判断は、画像を自分の目で見て行う。点数の表を判断の代わりにしない。着想を 1 文で言えない案は残さない。避けるもの（AI-slop のパターン、有名なロゴ、実行者が追加した、根拠のない制約）と、誤認の確認は `references/rounds-and-evaluation.md` §7〜8 に書いた。

利用者の要件に根拠のない制約を、実行者が自分で作らない。1 つ目の失敗では、製品の画面の規則（色は状態の表示にだけ使う）をシンボルマークにまで当てはめて、地味にした。審査の規則は原文で読む。「アプリ名またはブランドと一貫させる」を「名前の文字を使う」と拡大解釈したことも、失敗の原因だった。

## 運用の注意

サブエージェントは、同時に 2 体までにし、そのうち高性能モデルは 1 体までにする。これより多く動かすと、アカウントの rate limit（429）で全体が止まった。「案を並行させる」とは、1 つのラウンドの中で、着想と形が異なる複数の案を残すことであり、発想の種類ごとにサブエージェントを立てる意味ではない。案を描く作業は、高性能モデルの 1 体が複数の種類をまとめて担う。ホーム画面の確認画像と選定用の比較画像の生成・類似検索・参考ロゴの収集は、低コストモデルに任せる。描くサブエージェントは、自分の確認のために、画像を生成するスクリプトを実行してよい。ラウンドの評価（採用か不採用か）と、最終候補の内訳の点検は、実行者が画像を見て行い、サブエージェントに委譲しない。

作業ディレクトリ `logo-work/` は、git の対象外に置く。コミットするのは、工程 5 で書き出した成果物だけである。参考ロゴと、類似の確認で集めた他社のロゴは、比較にだけ使い、コミットも公開もしない。

所要時間の目安は、工程 0〜4 が 3 時間程度、工程 5 が 1 時間程度である。

## スクリプト

`scripts/` のスクリプトは、すべて実行するものである。ソースを読んで再実装しない。引数の詳細は `--help` と各 README に書いてある。

| 用途 | スクリプト | 何のために実行するか |
|---|---|---|
| 初回の準備 | `scripts/setup.sh` | 依存パッケージ・書体・chromium を用意する |
| ラウンドごとの確認 | `scripts/home-screen.mjs` | 案を参考ロゴの隣に置いたホーム画面のモックアップ（明るい画面の背景・暗い画面の背景）と、サイズ別の並べ比べを生成する |
| 最終候補の比較 | `scripts/candidate-comparison.mjs` | 表示場面ごとの行に全案を並べた 1 枚と、案ごとの 1 枚を生成する |
| 制作品質の修正 | `scripts/before-after.mjs` | 修正前後を並べた画像を生成する |
| 書き出し | `scripts/export-png.mjs` | SVG から必要なサイズの PNG を、ピクセル単位で書き出す |
| 類似の確認 | `scripts/similar/similar.mjs`（`--rot --out <dir>` を付ける） | 公開されているアイコン集との照合。`--rot` を付けると、回転・反転の 8 通りのうち最も高い類似度を採る |
| ロックアップ | `scripts/text2path/text2path` | ロゴタイプの文字を outline の path にする |

入力仕様・依存パッケージ・ライセンス・限界は、`scripts/README.md`、`scripts/similar/README.md`、`scripts/text2path/README.md` に書いた。類似検索の限界（画像検索と商標の図形検索ができないこと）は、利用者への報告に必ず書く。
