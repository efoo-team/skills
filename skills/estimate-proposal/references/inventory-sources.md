# 入力ソース別の棚卸し戦略（inventory-sources）

Phase 0〜1 で使う。**入力が議事録とは限らない。** ソースごとに「何が取れて、何が構造的に取れないか」が違うため、担保手段を変える。

## 1. ソース別の特性と担保手段

| ソース | 取れるもの | **構造的に取れないもの** | 担保手段 |
|---|---|---|---|
| 議事録・録画 | 業務の意図、痛み、使っていない機能の申告、意思決定の経緯 | 話題に出なかった機能（大半） | 稼働システムの実地調査で補完 |
| 稼働中のシステム | 実在する画面・導線・データ | 管理画面の中身、バッチ、外部連携、使用頻度 | ヒアリングと認証後領域の調査で補完 |
| RFP・要件定義書 | 客先が意識している要求 | 非機能、移行、運用、既存資産の実態 | §9 のチェックリストで補完 |
| 既存コードベース | ルーティング、スキーマ、バッチ、外部連携の全量 | どれが現役かの区別 | データ件数・ログでの実利用裏取り |
| 口頭ヒアリングのみ | 業務フローの主線 | 例外処理、周辺機能、非機能 | 業種別の標準機能チェックリストを当てる |

**単一ソースで棚卸しを完結させない。** 少なくとも2系統から引き、差分を突き合わせる。差分そのものが「客先が意識していない機能」または「使われていない機能」の発見になる。

## 2. 議事録・録画

- **全編を通読する。** 要約や検索だけで済ませない。機能の言及は雑談の中に紛れる
- 各行の証拠列に **発言箇所へのリンク**を残す。録画が Google Drive にあるなら `=HYPERLINK("https://drive.google.com/file/d/FILE_ID/view?t=SECONDS","00:38:07")` の形式でタイムスタンプ付きリンクにできる。客先レビュー時に「なぜこう書いたか」を即座に示せる
- **言及が無い行は空欄にせず `x` を入れる。** 空欄だと「調べていない」のか「言及が無い」のかが後から判別できない
- 「昔は使っていた」「今は使っていない」の発言は最優先で拾う。Phase 2 の廃止判定の一次証拠になる
- 議事録に**出てこなかった機能ほど廃止候補**である一方、単に話題が及ばなかっただけのことも多い。議事録の不在を廃止の根拠にしない

## 3. 稼働中のシステム

sitemap やトップページのリンクだけを見て結論を出すのは典型的な失敗である。**3方向から並列に調べる。**

1. **リンクBFS巡回** — トップから到達可能なページを幅優先で辿る。一覧ページの中のリンク（詳細ページへの導線）まで開く
2. **非リンクの標準パス** — そのフレームワーク／CMS の標準パスを直接叩く。導線が無いだけで生きているページがある（RSS、旧LP、規約類）
3. **認証後領域** — 検証用アカウントを作る（客先の許可を取る）。マイページ配下は導線が無い画面が残りやすい

調査時の規律：

- **URL は必ず HTTP ステータスで実在確認してから記録する。** 拡張子（`.php` 等）の付け忘れで404を客先に渡す事故が実際に起きている
- 注文・申込フローを検証する場合、**確認画面で止める。** 実データを作らない。触った場合はカートを空にし、レコードが作られていないことを確認する
- 「モックだけで機能実装が無い」ページを見分ける（クーポン一覧が常に空、レビュー投稿フォームはあるが表示実績ゼロ、など）。これは廃止候補の強い証拠になる
- 管理画面は原則見られない。**画面共有での説明を録画してもらう**のが最も効率が良い

## 4. RFP・要件定義書

- 記載機能をそのまま行にする。ただし RFP は**客先が意識している範囲**しか書かれていない
- §9 のチェックリストを当てて、非機能・移行・運用・権限の抜けを引き出す
- RFP の記載と現行システムの実態が食い違う場合、**食い違いそのものを行として起こす**（「RFP に記載があるが現行に存在しない」＝新規、「現行にあるが RFP に記載が無い」＝要確認）

## 5. 既存コードベース

機械的に全量を出せるのが強みだが、**現役かどうかは分からない**のが弱み。

| 抽出対象 | 見る場所 |
|---|---|
| 画面 | ルーティング定義、テンプレートディレクトリ |
| データ概念 | マイグレーション、スキーマ定義 |
| バッチ・定期処理 | cron 定義、スケジューラ設定、キュー定義 |
| 外部連携 | 環境変数、API クライアント、Webhook エンドポイント |
| 帳票 | PDF/CSV 生成処理 |

実利用の裏取り：

- テーブルの行数・最終更新日時（0件や数年前で止まっているものは廃止候補）
- アクセスログでの該当パスのヒット数
- 管理画面の操作ログ

## 6. 口頭ヒアリングのみ

最も漏れやすい。**業種別の標準機能を先に用意して当てる。**

例（予約・受講管理業の場合）: 会員登録／ログイン／パスワード再発行／退会、商品（講座）登録／カテゴリ／在庫（定員）、予約・キャンセル・振替・キャンセル待ち、決済（カード／コンビニ／銀行）、返金・取消、リマインド通知、帳票（出席簿・名札）、精算（外部パートナーへの支払）、CMS（お知らせ・ブログ）、問い合わせ、メルマガ、アクセス解析。

「御社では◯◯はどうされていますか」と聞くと、システム外（Excel・LINE・手作業）で回している業務が出てくる。**それは機能ではないが、Phase 2 の「新規」判定に直結する**（§ disposition-and-normalization の業務基準ルール）。

埋まらない箇所は推測で埋めず `【要確認】` で残す。

## 7. 複合ソースのマージ

- 詳細一覧は **1本に統合する。** ソースごとに別シートを作らない（重複と漏れの温床）
- 同じ機能が複数ソースから出た場合、証拠列に**複数の証拠を併記する**（強い根拠になる）
- ソース間で矛盾したら **実物 > 一次資料 > 発言** の順で信頼する。ただし「実物にあるが誰も使っていない」ケースがあるので、実物の存在は実利用を意味しない
- 網羅の完了判定：新しいソースを1つ足しても新規行が出なくなったら打ち切る。1ソースで打ち切らない

## 8. 証拠列の書き方

| 状態 | 書き方 |
|---|---|
| 議事録に言及あり | タイムスタンプ付きハイパーリンク |
| 言及なし（調査済み） | `x` |
| サイトで実在確認 | 確認済みの完全URL |
| コードから抽出 | `path/to/file.php:123` |
| 未調査 | 空欄のまま残さない。行を作った以上、必ずいずれかを入れる |

## 9. 非機能・移行・運用の補完チェックリスト

機能の棚卸しでは必ず抜ける領域。行として明示的に起こす（積算対象になるため）。

- **インフラ**: 本番／ステージング環境、ドメイン・SSL、バックアップ、監視、ログ
- **セキュリティ**: 認証方式、権限設計、個人情報の取扱、脆弱性対応
- **データ移行**: 対象データの種類ごと、移行元からのエクスポート可否、整合性検証、廃止機能に紐づくデータの扱い
- **外部連携**: 決済、メール配信、動画配信、SMS、会計、アクセス解析
- **運用**: 管理者の役割と権限、定型オペレーションの手順、障害時の連絡経路
- **品質保証**: 単体・結合テスト、外部連携の受入テスト（UAT 支援などクライアント側の工数を要する工程は、求められた場合のみ行として起こす）
- **既存の手作業・RPA**: システム外で回っている業務。システム標準機能へ置換するのか、運用継続なのかを必ず決める
