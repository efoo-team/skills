# 見積書兼提案書の書き方（proposal-writing）

Phase 6 で使う。雛形は [../assets/proposal-template.md](../assets/proposal-template.md)。本ファイルは**各章を何で埋めるか、どこで判断が要るか**を扱う。

大原則: **積算の詳細（pt・係数・単価・工数・削減率）は見積書に書かない。** 開示は機能群単位の小計と合計まで。根拠はスプレッドシートに内部資料として持ち続ける。

## 1. 章立てと入力ソースの対応

**Phase 6 は判断をする工程ではない。** 前工程の成果物を章に割り付けるのが仕事である。

| 章 | 何から取るか |
|---|---|
| 書誌情報 | 客先サイトの会社概要・自社サイトの会社概要・§2 の既定値 |
| 1. エグゼクティブサマリー | スコープ集計＋ユーザーが決めた提示額 |
| 2. 現状認識と目的 | Phase 0〜1 の調査記録（議事録・実地調査） |
| 3. スコープ | 正規化シート（機能名・含まれる要素）＋詳細シートの方針集計。**pt 列は載せない** |
| 4. 実施しないこと | 詳細シートの方針=廃止 の行（機能名・機能概要・方針メモ） |
| 5. お見積金額 | Gate D で合意した機能群集約表（estimation-model.md §13）＋提示額 |
| 6. スケジュール | **入力が無ければ要確認マーカー** |
| 7. 実施体制 | **入力が無ければ要確認マーカー**。自社の関連実績は一次情報で確認したものだけ |
| 8. 前提条件 | Phase 0〜2 で判明した案件固有の事実＋§8 の定型項目 |
| 9. 留意事項 | §8 の定型文 |

数値はすべてシートから取る。**暗算しない。** 機能群別金額・フェーズ別金額の合計が提示額と一致することを確認する。

**お支払い条件の章は置かない。** 支払条件（分割回数・支払サイト）は見積書で約束せず、契約書（ご契約時の協議）に委ねる。留意事項の「契約条件は別途締結する契約書に定める」の一文がこれを受ける。

**別紙としてスプレッドシートのリンクを載せない。** シートには単価・pt・係数が含まれるため、リンク共有は内訳非開示と両立しない。スコープの共有が必要な場合は、棚卸し（詳細一覧・方針判定）タブのみを複製した共有用シートを別途作る。

## 2. 書誌情報の埋め方

| 項目 | 扱い |
|---|---|
| 宛先 | 客先の**法人正式名称**。サイトの会社概要／特商法ページで確認する。店舗名と法人名が違うことが多い |
| 件名 | 案件の内容を1文で。スコープの大カテゴリを反映させると具体的になる |
| 見積番号 | **採番規則が確認できていない場合は `【要確認：見積番号】`**。勝手に番号を作らない |
| 発行日 | 作成日 |
| 有効期限 | **自社の商習慣を確認してから決める。** 未確認の場合は `【要確認：自社の商習慣による有効期限】` を置き、固定値を入れない |
| 提出者 | 自社の法人名・所在地・代表者・本件担当。自社サイトの会社概要で確認する |

> 有効期限・検収期間は「一般的にそうである」というだけの値を既定値として置かない。**自社の商習慣を確認するまで、確認用マーカー（`【要確認】`）のまま残し、固定値を入れない。** 商習慣が確定したらこのファイルを更新して既定値を確定させる。

## 3. エグゼクティブサマリー

1枚（表1つ）で以下が分かる状態にする。読み手が最初に知りたいのは金額と範囲である。

- 対象範囲（棚卸し件数 → 正規化後の件数 → うち作らない件数）
- 主な変更点（3点程度）
- **お見積金額**
- 想定期間

**開発工数（pt・人日・人月）の行を置かない。** 工数は内部情報であり、開示すると単価が逆算できてしまう。

サマリーの直後に、この提案の性格を1〜2文で書く。売り文句ではなく事実を書く。例:「全機能を棚卸しし、何を作り何を作らないかを先に確定させている」「作らないものの確定が費用と期間を圧縮する最大の要因である」。

## 4. 課題認識の書き方

**客先が言っていない課題を書かない。** 調査で見つけた事実は書いてよいが、価値判断を足さない。

| 悪い | 良い |
|---|---|
| 古くて使いづらいシステムです | サポート終了世代であり、セキュリティ更新・機能追加のいずれも困難 |
| 属人化していて危険です | 外部のRPAと人手で運用されており、担当者が変わると継続できない |
| 機能が多すぎます | 過去の事業形態の名残が管理画面に残り続け、運用者の認知負荷になっている |

課題は表で6件前後。多すぎると論点がぼやける。各行に「現状の具体例」列を置き、抽象論にしない。

課題のあとに目的を3点程度で書く。目的は「作り直す」ではなく**事業として何が変わるか**で書く。

## 5. 「実施しないこと」章の作り方

この章が本提案の中心である。独立した章として立てる（スコープ章の小節にしない）。

構成:

1. **廃止する機能の表**（機能名＋廃止理由）。理由は Phase 2 の方針メモをそのまま使う
2. 実利用が確定できなかったものには注記を付ける:
   > 上記◯・◯については、実地調査の範囲では利用実績を確認できませんでした。実際にご活用の実績がある場合は、スコープに戻したうえで再見積いたします。
3. **費用に含まれないもの**（区分別）。外部サービス利用料／コンテンツ制作／施策運用／運用保守／システム連携／その他

冒頭に一文置く: 「リニューアルの費用と期間を圧縮する最大の要因は、作らないものを先に確定させることです。」

## 6. 内訳の開示方針

開示のレイヤーは3段階あり、**見積書に載せるのは上2つだけ**である。

| レイヤー | 内容 | 開示 |
|---|---|---|
| スコープ | 全機能の棚卸し・方針判定・実装対象一覧 | **全件開示**（3〜4章） |
| 機能群小計 | 8〜12群の機能群と各群の金額 | **開示**（5章） |
| 積算詳細 | pt・係数・単価・工数・削減率・リザーブ | **非開示**（シート内部のみ） |

積算詳細を開示しない理由（実案件での判断）:

- **単価はクライアント業界の人件費相場と乖離しうる。** 飲食系クライアントに対する時間単価1万円は、同業界の人材単価との差が極めて大きく、金額の妥当性より先に違和感が立つ
- 工数（人日・人月）を開示すると単価が逆算できるため、工数も載せない
- 透明性はスコープの全件開示（作る・作らないの明示）で担保する。内訳の透明性と単価の開示は別問題である

**見積書の完成後、本文を全文検索して pt・ポイント・単価・削減率・人日・人月・係数・算定・リザーブの語が残っていないことを確認する。**

## 7. お見積金額章の構成

構成は4節。数字はすべて Gate D で合意した機能群集約表から転記する。

1. **機能群別内訳** — 表: # / 機能群 / 対象機能 / 金額（税抜）＋合計行。各群に対象機能名を併記し、スコープ章との対応を追跡可能にする。表の下に注記: 「各機能群の金額には、要件定義・設計・実装・進行管理の費用を按分して含んでいます。」
2. **総額** — 税抜・消費税・税込の3行。直後に: 「本見積は概算です。要件定義完了時点で確定見積を提示し、金額に増減が生じる場合は、ご協議のうえ調整いたします。」（リザーブの存在はこの一文に織り込まれており、内訳としては書かない）
3. **段階リリース（フェーズ分割）の選択肢** — 提案する場合のみ。分割は機能群単位。**単一リリース案と段階リリース案の総額を再積算して一致したことを確認してから**、「分割による総額の増加は発生しない」と説明する。追加のリリース・テスト・移行・調整工数を再積算せずに「構成上増えない」と書かない。未確認なら `【要確認：分割による総額の増減】` にする
4. **【参考】補助金を活用した場合の自己負担イメージ** — 論点になっている場合のみ。「試算であり採択・交付を保証しない」を必ず添える

## 8. 前提条件とスコープ外

前提条件は「これが違ったら再見積になる」ことを列挙する。案件固有の事実（Phase 0〜2 で判明したもの）を先に、定型項目を後に置く。

定型項目:

- 本見積の根拠（いつのヒアリング・どの調査に基づくか）
- 移行先サービスの選定・契約は客先が行うこと
- 外部サービスの継続利用前提
- デザインの範囲（既存踏襲かブランド刷新か）
- データ移行の対象範囲と、現行ベンダーからのデータ提供が受けられること
- 廃止機能に紐づくデータは移行対象外であること
- コンテンツ（文章・画像）の新規制作は含まないこと
- 客先側の意思決定担当者の設定（回答遅延はスケジュールに影響する旨）
- 検収期間（**要確認：自社の商習慣。案件ごとに確認してから記載し、未確認なら `【要確認】` を置く**）

スコープ外は区分ごとに表で示す。「その他」に逃さず、思い当たるものは具体的に書く。

**求められていない工程を前提条件やスケジュールに紛れ込ませない。** UAT支援・テスト報告書・運用マニュアル等は、クライアントが明確に求めたときだけスコープに入れる。品質確認は開発側のテストと定例での報告で担保する（スケジュールの成果物欄は「テスト結果・改善報告（定例にてご報告）」のような形にする）。

## 9. 自社情報・客先情報の扱い

- **社名・住所・代表者名を記憶から書かない。** 必ず一次情報（客先サイト・自社サイト）で確認する
- 自社の関連実績を書く場合、**確認できた事実だけ**を1〜2文で書く。「豊富な実績」「多数の導入」のような検証不能な表現を使わない
- 客先の担当者名は、議事録等で確認できた表記をそのまま使う
- 文書に載せる URL は必ず HTTP ステータスで実在確認する

## 10. 参考文献の扱い

- **様式の参考文献（他社ブログ・テンプレート記事）は見積書本文に載せない。** 客先向け文書に自社の作業過程を書くのは不自然である
- **案件の根拠となる情報源は本文に明記する。** ヒアリング日時、実地調査、確認したデータ（「全サンプルで投稿表示ゼロ」など）
- 様式の出典は**チャット報告と作業ログに残す**。後から様式の根拠を追えるようにする

## 11. トーンの規律

- 自社の売り込みを本文の主旋律にしない。**スコープの全件開示（作る・作らないの明示）が訴求点**になる構成にする
- 検証不能な形容（豊富・最先端・圧倒的）を使わない
- 「一式」を使わない
- 想定・案は必ずそう明記する。ただし本文に「想定」と書いただけでは読み手に伝わりにくいので、**確定していない項目は要確認マーカーで残し、人が埋めてから提出する**
- 客先の現行ベンダーを批判しない。事実（サポート終了世代である等）だけを書く
- **ITジャーゴン・専門語を使わず、一般的な日本語にする。** 読み手はクライアントの業務担当者であり、IT専門家ではない。実際に修正指示を受けた例: 分界→区分、リストア→データ復元、課金→ご請求。書き終えたら客先の担当者が読む前提で通読する

## 12. 提出前チェックリスト

```
- [ ] 「一式」という語が本文に無い
- [ ] pt・ポイント・単価・削減率・人日・人月・係数・算定・リザーブの語が本文に無い（全文検索で確認）
- [ ] ITジャーゴンが残っていない（分界・リストア・課金など、業務担当者に馴染みのない語）
- [ ] 機能群別内訳・フェーズ別内訳の合計が提示額と一致する
- [ ] 機能群の集約は Gate D で合意したものと一致する
- [ ] 廃止機能の表に全件が載っている（詳細シートの方針=廃止 の件数と一致）
- [ ] 求められていない工程・成果物（UAT支援・報告書等）が紛れ込んでいない
- [ ] スプレッドシートへのリンクが本文に無い
- [ ] 要確認マーカーが残っていないか確認し、残るものは報告で列挙した
- [ ] 社名・住所・担当者名を一次情報で確認した
- [ ] 本文中の全 URL を HTTP ステータスで確認した
- [ ] 様式の参考文献が本文に混入していない
- [ ] Google Docs で表がネイティブ表になっている・見出し階層が保たれている
- [ ] 入力なしに自分が埋めた項目を、ユーザーへの報告で全て列挙した
```
