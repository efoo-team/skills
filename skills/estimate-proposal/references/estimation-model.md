# 積算モデルと標準係数（estimation-model）

Phase 4〜5 で使う。**係数は実績に基づく既定値であり、案件ごとに上書き可能**。ただし上書きするときは §8 の規律に従う。

本ファイルの内容（pt・係数・単価・換算）はすべて**シート内部の情報**である。見積書に記載するのは §13 で集約した機能群単位の金額までであり、積算の詳細を客先に開示しない。

## 1. 積算の全体式

| ステップ | 算出するもの | 計算内容 |
|---|---|---|
| ① | 基本pt | 実装担当 × 難易度 |
| ② | オプションpt | CRUD・CSV出力・バッチ処理・帳票印刷の有無に応じて加算 |
| ③ | 画面pt | ページ数 × UI複雑度の単価 |
| — | **小計pt** | ① ＋ ② ＋ ③ |
| ④ | AI削減率 | 作業タイプ別の削減率 |
| — | **最終工数pt** | 小計pt ×（1 − AI削減率） |
| ⑤ | PM係数 | ×1.2 |
| — | **積算工数pt** | 最終工数pt × PM係数 |

## 2. 基本ポイント（実装担当 × 難易度）

| 実装担当 | 低 | 中 | 高 |
|---|---|---|---|
| 両方（フロントエンド＋バックエンド） | 2 | 4 | 8 |
| バック（バックエンドのみ） | 1 | 3 | 6 |
| インフラ | 1 | 2 | 4 |

**「両方」は画面とサーバ処理の両方を作る機能**を指す。管理画面の CRUD もユーザー画面も基本は「両方」。バッチ・連携基盤など画面を持たないものが「バック」。

難易度の目安：

| 難易度 | 判定 |
|---|---|
| 低 | 標準的な一覧・詳細・登録編集。判断ロジックが無い |
| 中 | 業務ルールに基づく分岐がある。複数エンティティにまたがる |
| 高 | 状態遷移・在庫引当・金額計算・外部システムとの整合など、間違えると事故になるロジックを含む |

## 3. オプションポイント

| 要素 | 加算pt |
|---|---|
| CRUD（登録・編集・削除の一式） | +1 |
| CSV出力 | +1 |
| バッチ処理（定時実行・一括処理） | +2 |
| 帳票印刷（PDF出力） | +1 |

**主目的除外ルール**: その処理自体が機能の主目的である場合は加算しない（二重計上になるため）。作業タイプが `定型処理` の行では CSV・バッチ・帳票の加算を行わない。例: 「出欠・帳票管理」の CSV 出力はその機能の主目的なので加算しない。

## 4. 画面ポイント

`ページ数 × UI複雑度の単価` で加算する。

| UI複雑度 | 1ページあたり | 該当例 |
|---|---|---|
| 高 | +3 | 検索・絞込・多状態表示を伴う一覧、動画プレイヤー |
| 中 | +1 | 詳細ページ、マイページ、フォーム |
| 低 | +0.5 | 管理画面の標準的なマスタ画面 |
| ー | 0 | 画面を持たない（バッチ・基盤・非機能） |

ページ数は**実装する画面の数**であり、URL の数ではない。一覧と詳細は2ページ、確認画面を挟むフォームは2ページと数える。

## 5. AI削減率（作業タイプ別）

一律の割引をかけない。**削減効果は作業の性質で桁が変わる**ため、作業タイプごとに率を持つ。

| 作業タイプ | 削減率 | 理由 |
|---|---|---|
| 定型CRUD | 80% | パターンが確立しており生成が最も効く |
| 定型処理（バッチ・帳票） | 75% | 仕様が明確で生成しやすい |
| 独自ロジック | 60% | 業務要件の読み解きと設計判断に人手が要る |
| デザインUI | 50% | 意匠の判断と調整に人手が要る |
| データ移行 | 50% | 実データの検証・突合に人手が要る |
| テスト | 60% | ケース生成は効くが受入判断は人手 |
| インフラ | 60% | 構成のコード化で効率化するが検証は人手 |
| 外部連携 | 40% | 外部仕様の制約・検証環境の都合に依存し、効率化が効きにくい |

作業タイプは各行に1つだけ付ける。複数該当するときは**最も削減率が低いもの**を選ぶ（決済連携を含む機能は「外部連携」）。

## 6. 特性列の定義

正規化シートに持たせる列。

| 列 | 値 | 用途 |
|---|---|---|
| 実装担当 | 両方／バック／インフラ | 基本pt |
| 難易度 | 低／中／高 | 基本pt |
| ページ数 | 整数 | 画面pt |
| CRUD | ✓ / 空 | オプションpt |
| CSV出力 | ✓ / 空 | オプションpt |
| バッチ処理 | ✓ / 空 | オプションpt |
| 帳票印刷 | ✓ / 空 | オプションpt |
| 外部依存度 | なし／中／高 | 参考情報（積算には直接使わない。リザーブ判断の材料） |
| 移行データ | ✓ / 空 | 参考情報（データ移行行の規模判断に使う） |
| UI複雑度 | 高／中／低／ー | 画面pt |
| 作業タイプ | §5 の8種 | AI削減率 |
| 小計pt | 数式 | ①＋②＋③ |
| AI削減率 | 数式 | 作業タイプから引く |
| 最終工数pt | 数式 | 小計pt ×（1−削減率） |

## 7. セル数式

係数表は同じシートの右側（例: V〜Y列）に置き、数式から `INDEX`/`MATCH` で引く。**係数をベタ書きしない**（変更時に全行を直すことになる）。

小計pt（行6の例。列は実際のレイアウトに合わせる）:

```
=IF($G6="","",
   INDEX($W$3:$Y$5, MATCH($G6,$V$3:$V$5,0), MATCH($H6,$W$2:$Y$2,0))
 + IF($J6="✓",1,0)
 + IF(AND($Q6<>"定型処理",$K6="✓"),1,0)
 + IF(AND($Q6<>"定型処理",$L6="✓"),2,0)
 + IF(AND($Q6<>"定型処理",$M6="✓"),1,0)
 + $I6*IFERROR(INDEX($W$8:$W$11,MATCH($P6,$V$8:$V$11,0)),0))
```

AI削減率:

```
=IF($G6="","",IFERROR(INDEX($W$14:$W$21,MATCH($Q6,$V$14:$V$21,0)),""))
```

最終工数pt:

```
=IF($R6="","",$R6*(1-$S6))
```

規律：

- **全データ行に同じ数式を入れる。** 1行でも手入力の数値が混ざると、係数を変えても追随せず総額が静かにずれる（唯一の例外は §9 の非機能3行の小計pt）
- **空欄ガード（`IF($G6="","",…)`）を必ず入れる。** 未入力行がエラーや0で紛れ込むのを防ぐ
- **行の数式に `ROUND` を置かない。** 丸めは最終表示の1回だけ。行ごとに丸めてから合計すると誤差が累積する
- 合計行は生の合計（`SUM`）から取る。丸めた値を連鎖させない

## 8. 係数を変えるときの規律

案件特性に応じて上書きしてよいが、以下を守る。

- **目標金額に合わせて係数を動かさない。** 積算は積算として出し、差額は提示額の判断（§11）で吸収する
- 変更した係数と理由をシート上に残す（係数表の隣にメモ列を置く）
- AI削減率を上げるときは「なぜこの案件では効くのか」を言えるようにする。既存コードの移植が多い、仕様が完全に確定している、など
- **法改正・規制対応を含む機能は削減率を下げる**（要件の読み解きが人手の仕事になるため）

## 9. 非機能・移行・品質の扱い

インフラ構築・データ移行・テスト／品質保証は、**基本pt行列では測れない**。画面数もCRUDも無く、難易度だけでは規模が決まらないためである。この3行だけは規模ベースで直接 pt を置く。

| 行 | 規模の決め方 | 目安 |
|---|---|---|
| インフラ構築 | 環境数（本番／STG）＋ 監視・バックアップ・セキュリティの要否 | 標準構成で 6pt 前後 |
| データ移行 | 移行対象データの**種類数** × 整合性検証の重さ | 種類ごと 3〜4pt、5種類で 18pt 前後 |
| テスト・品質保証 | 正規化後の機能数と、外部連携の受入テストの有無 | 機能数の 0.5〜0.7倍pt |

規律：

- **小計pt に直接入力してよいのはこの3行だけ。** 機能行で直接入力したくなったら、それは特性列の設定が間違っているサイン
- **直接入力した根拠を必ずシートに残す**（「含まれる要素」に「移行対象5種」等を書く）。根拠が無い直接入力は、後から誰も検証できない
- AI削減率と最終工数pt は、この3行でも**数式のまま**にする（削減率は作業タイプから引く）
- `verify_estimate_sheet.py` は小計pt の直接入力を WARN として列挙する。WARN が出た行について、上記の根拠がシートにあるかを目視で確認する

## 10. 金額化（PM係数・工数換算・単価）

| 項目 | 標準値 | 備考 |
|---|---|---|
| PM係数 | ×1.2 | 進行管理・仕様調整・定例・課題管理 |
| 人日換算 | 1pt = 0.5人日 | |
| 1人日 | 8時間 | |
| 1人月 | 20人日 | 営業日ベース |
| 時間単価 | 10,000円 | 人日単価 80,000円に相当 |

**換算前提は必ずシート上のセルとして明示する。** ラベルと数式の実体がずれる事故が実際に起きている（`人日単価 ¥10,000` というラベルのセルが、数式では8時間を掛けた時間単価として使われていた）。金額に関わるセルは `--render FORMULA` で実体を読んで確認する。

1人月を12人日などの非標準値にしない。参考シートから引き継いだ値がある場合は必ず疑う。

## 11. 不確実性リザーブ

積算額は**要件が全て確定した場合の理想値**である。実際には要件定義前の不確実性が残るため、係数を掛けて提示額を作る。

- 標準は **×1.5**（要件定義前・既存システム刷新・外部連携の移行先未定を含む案件）
- **リザーブが吸収する不確実性の要因を列挙できないなら、その倍率を使わない。** 列挙できる例:
  - 要件定義による詳細化（ヒアリング時間が短い、例外パターンが未把握）
  - 外部サービスの移行先未定（API仕様・与信タイミング・返金APIの有無で工数が変動）
  - データ移行の実データ差異（長期運用データの欠損・重複・表記ゆれ）
  - 廃止機能の最終確定待ち
  - 現行ベンダーからのデータ提供条件
- 要件が確定している案件（RFP が詳細、既存システムの改修範囲が明確）では 1.2〜1.3 に下げる
- **提示額の最終決定はユーザーが行う。** 積算額とリザーブ後の額を提示し、端数調整も含めて判断を仰ぐ

## 12. フェーズ分割の算出

段階リリースを提案する場合、**機能群の単位で分割し、最終工数pt の構成比で金額を按分する**。

- 分割は機能群（§13）の単位で行う（群の一部を分けない）
- 共通基盤（決済連携基盤など）は先行フェーズに置く。後続フェーズが基盤の上に乗る形にすれば、分割による総額の増加は発生しないと説明できる
- 按分後の各フェーズ金額の合計が提示額と一致することを確認する（端数調整はどちらか一方に寄せる）

## 13. 開示用の機能群集約と金額按分

見積書に載せるのは、正規化した機能（30〜50行）をさらに集約した**機能群単位の小計と合計**である。手順:

1. 正規化した機能を、業務のまとまりで **8〜12 の機能群**へ集約する
2. 機能群ごとに最終工数pt を合計する
3. `提示額 × 群pt ÷ 総pt` を計算し、**万円単位に丸める**
4. 丸め後の合計と提示額の差額を確認する。差があれば**最大の群**で吸収する（複数の群をいじらない）
5. 合計が提示額と完全一致することを検算してから見積書に転記する

集約の指針:

- **8〜12群が目安。** 少なすぎると「一式」に近づいて内訳の意味を失い、多すぎると詳細開示に戻ってしまう
- 群の切り口は業務のまとまりで決める。実績のある切り方: 管理基盤（認証・権限・アプリ基盤）／管理画面の業務機能／受注・キャンセル・精算／コンテンツ・顧客対応／公開サイト／申込・会員機能／動画サブスクリプション／決済・自動処理基盤／インフラ・データ移行／テスト・品質保証
- 各群に**対象機能名を併記**し、スコープ章の機能一覧との対応を追跡可能にする
- **群の切り方はユーザーの感覚と食い違いやすい**（実案件で提出前に組み替えが発生した）。Gate D で必ず表（群名・対象機能・金額）を見せて合意を得る
- 按分結果として極端に小さい群（例: 20万円未満）が出たら、実体のある作業（基盤構築等）を群に含めて説明がつくようにするか、隣接群への統合を検討する

按分の規律:

- 按分は**機械的に pt 構成比で行う**。群単位で金額を「気持ちで」盛らない。金額を動かしたい場合はユーザーの判断として動かし、合計一致だけは必ず守る
- シート上に按分計算の作業列（群名・群pt・按分額・丸め額）を残し、見積書の数字がどこから来たかを追跡可能にする
