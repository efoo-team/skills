## 1. 方針の5分類

| 方針 | 定義 | 積算への影響 |
|---|---|---|
| 踏襲 | 現行の業務フローをそのまま新システムで再現する | 通常の実装工数 |
| 改良 | 現行の課題（手作業・制約・使いにくさ）を解消したうえで実装する | 通常＋設計判断のぶん難易度が上がりやすい |
| 新規 | 現行に存在せず、業務としても行われていない。今回新設する | 難易度・不確実性ともに高い |
| 統合 | 別機能へ吸収し、管理箇所を一本化する | 吸収先に含めて計上。単独では積算しない |
| 廃止 | 今回は実装しない | 積算対象外。正規化シートに載せない |

この5つ以外を作らない。特に「保留」を作らない（§4）。

## 2. 新規の判定は業務基準で行う

**システムに機能が無いこと ≠ 新規。** 判定はシステム基準ではなく業務基準で行う。

| 現状 | 判定 |
|---|---|
| システムに無く、業務としても行っていない | **新規** |
| システムに無いが、Excel・手作業・外部サービス・ベンダー依頼で行っている | **改良**（システム化による既存業務の置換） |
| システムにあるが使いにくい／制約がある | **改良** |
| システムにあり、そのままで良い | **踏襲** |

この区別が重要なのは、**「業務として既に回っている」ものは要件が既に存在する**からである。要件をゼロから作る新規とは不確実性が桁違いで、それが積算の難易度・AI削減率に効いてくる。

判定に迷ったら「客先はこの業務を今どうやっているか」を聞く。「やっていない」なら新規、「◯◯で回している」なら改良。

## 3. 廃止の判定根拠

廃止は最も金額を動かす判定なので、**根拠の型を揃える**。

| 根拠の型 | 例 | 強さ |
|---|---|---|
| 客先が明言 | 「抽選はもう何年も使っていない」 | 最強 |
| 実データで裏取り | 投稿件数ゼロ、テーブル0件、数年前で更新停止 | 強 |
| 事業形態の変化 | 1校舎になったので校舎切替は不要 | 強 |
| 代替手段の存在 | 外部サービス・別チャネルの運用を継続する | 強 |
| 未実装（モックのみ） | 画面はあるが機能が入っていない | 強 |
| 導線が無い | 画面は生きているがどこからも辿れない | 中（要確認を付ける） |
| 自分の推測 | 「たぶん使っていない」 | **根拠にしない** |

自分で確定できないものは廃止候補のまま `要クライアント確認` を明記して提示する。判断を避けて「踏襲」に倒すのは、客先の費用を増やす判断であることを自覚する。

## 4. 保留を作らない

「保留」は判断ではなく判断の先送りである。保留のまま Phase 3 に進むと、積算対象か対象外かが決まらず、後で全体をやり直すことになる。

判断できないときの扱い：

- 情報が足りない → 何を確認すれば決まるかを方針メモに書き、**現時点で最も妥当な方針に倒す**
- 客先判断が必要 → 方針を仮置きしたうえで `要クライアント確認` を付ける
- 統合先が未定 → 統合ではなく踏襲に倒し、Phase 3 の集約で解決する

## 5. 方針メモの書き方

方針メモは内部メモではなく、**客先向け文書にそのまま転記される文である**。

- 廃止行のメモ → 見積書「廃止理由」列
- 新規行のメモ → 見積書「新規構築する機能」表の内容
- 統合行のメモ → 見積書「統合する機能」表の理由

書き方の例：

| 悪い | 良い |
|---|---|
| 使ってなさそう | 数年間の利用実績ゼロ |
| いらない | 1校舎運営のため不要 |
| 外部でやってる | 外部サービスでの運用を継続 |
| モック | 現行はモックのみで機能実装なし |

20〜30字で、理由が読み手に伝わる形にする。

## 6. 粒度正規化の考え方

棚卸し直後の一覧には、必ず以下が混在している。

- 機能（例: 講座管理）
- 機能の中の設定項目（例: 材料費設定、受付開始日時）
- 機能の中の1操作（例: 講座登録・編集）
- 機能をまたぐ横断概念（例: カテゴリ）

このまま積算すると、**たまたま細かく分解された領域だけ pt が積み上がる**。今回の実案件では、詳細104行での積算と正規化34機能での積算で総額が約1.4倍違った。粒度は金額に直結する。

正規化の原則：**「管理画面の1メニュー」または「ユーザーが認識する1つの体験」を1行にする。** その中で提供する能力は「含まれる要素」へ落とす。

## 7. 命名規約

表記が揺れると、一覧を見た瞬間に「機能単位で整理されていない」と分かってしまう。

| 領域 | 規約 | 例 |
|---|---|---|
| 管理画面 | `◯◯管理` | 講座管理、受注管理、講師精算管理 |
| ユーザー画面 | 名詞（画面・体験の名前） | 講座一覧・検索、マイページ、動画視聴 |
| 共通・自動処理 | `◯◯基盤` または `◯◯処理` | 決済連携基盤、自動通知メール |
| 非機能 | 工程名 | インフラ構築、データ移行、テスト・品質保証 |

**操作を機能名にしない。**「講座登録・編集」は機能ではなく操作なので、`講座管理` の含まれる要素へ落とす。

## 8. 含まれる要素の書き方

セル内で改行し、`・` 始まりの箇条書きにする。

```
・基本情報（タイトル・本文・注意事項・持ち物・画像）
・講座種別（単体/コース）
・材料費設定
・受付開始日時
・先行受付リンク発行
```

- **その機能が提供する能力**を列挙する。実装タスクを書かない
- 客先が読んで「自分たちの業務がここに入っている」と分かる言葉にする
- 5〜9項目が目安。10を超えたら分割を検討する（ただし画面が1つなら分割しない）

## 9. 集約の判断基準

| 状況 | 判断 |
|---|---|
| 同じ画面で操作する | 集約する |
| 同じ概念の属性・設定である | 集約する（例: 受付設定 → 講座管理） |
| 独立したページ・独立した体験になる | 分ける（まとめすぎない） |
| 複数機能から参照される辞書・区分 | `マスタ管理` として切り出す |
| 状態が違うだけで実体は同じ | 集約する（例: コース講座 → 講座管理の講座種別） |
| 実装担当・難易度が大きく違う | 分ける（積算精度が落ちるため） |

判断に迷ったら **「客先の管理画面のメニューに何個並ぶか」** を想像する。それが行数に近い。

## 10. 正規化シートの列構成

| 列 | 内容 |
|---|---|
| No. | 通し番号 |
| 大カテゴリ | 管理画面／ユーザー画面／共通・自動処理／非機能・移行・品質 |
| 機能名 | §7 の命名規約に従う |
| 含まれる要素 | §8 の箇条書き |
| 対応詳細No | 詳細一覧のどの行を吸収したか（追跡用） |
| （以降） | 積算の特性列。[estimation-model.md](estimation-model.md) を参照 |

**対応詳細No は必ず入れる。** 客先から「あの機能はどこに入ったのか」と聞かれたときに即答できるのと、廃止漏れ・集約漏れの検査に使えるのが理由。詳細一覧の全行が「いずれかの正規化行に吸収されたか、廃止と判定されたか」のどちらかになっていることを確認する。
