## 1. シートの構成

1つのスプレッドシートに2タブを持たせる。

| タブ | 役割 | 行数の目安 |
|---|---|---|
| 機能一覧 | 詳細一覧。棚卸しの全量。証拠列と方針列を持つ | 100〜150行 |
| 機能一覧（正規化） | 積算対象。機能単位。特性列と pt 列を持つ | 30〜50行 |

**このシートは内部資料であり、客先に共有しない**（正規化タブに単価・pt・係数が載っているため）。見積書にもリンクを載せない。スコープの共有が必要な場合は、機能一覧（棚卸し・方針判定）タブだけを複製した共有用シートを別に作る。タブ単位の閲覧制限では防げないことに注意する（閲覧権限はスプレッドシート全体に及ぶ）。

**シートは純粋な行列にする。** 説明文の行・凡例の行・カテゴリ区切りの空行を挟まない。説明が必要なら別タブか見積書側に書く。係数の参照表は同じタブの右側（データ列から離れた列）に置く。

タブ名は操作のたびに読み上げて確認する。詳細タブと正規化タブを取り違えて再計算した事故が実際に起きている。

## 2. gog sheets の落とし穴

| 事象 | 正しい書き方 |
|---|---|
| `--range` フラグは存在しない | 範囲は**位置引数**で渡す: `gog sheets get <id> "'タブ名'!A1:T45"` |
| `--values-json` が1次元配列を拒否する | 常に2次元配列で渡す: `[["値"]]`。1次元だと `json: cannot unmarshal string into Go value of type []interface {}` |
| `delete-dimension` が確認を求めて止まる | `--force` を付ける |
| タブ名に括弧や全角を含むとレンジが壊れる | タブ名をシングルクォートで囲む: `"'機能一覧（正規化）'!A1:C10"` |

主なサブコマンド: `get` / `update` / `insert` / `format` / `add-tab` / `delete-dimension`。タブ一覧は `gog sheets tabs` ではなく **`gog sheets metadata <id>`** で見る。

## 3. 多行セルを含むシートの読み取り

「含まれる要素」列はセル内改行を含むため、**プレーンテキスト出力を行単位でパースすると列がずれる**。必ず JSON で受けてから処理する。

```bash
gog sheets get <id> "'機能一覧（正規化）'!A1:T45" --json --results-only > /tmp/norm.json
python3 -c "
import json
d = json.load(open('/tmp/norm.json'))
v = d['values'] if isinstance(d, dict) else d
for i, r in enumerate(v, 1):
    print(i, '|', '|'.join(str(c).replace(chr(10), ' / ') for c in r))
"
```

レスポンスが `{"values": [...]}` の形か素の配列かはコマンドによって違う。両方に対応する分岐を入れておく。

## 4. 数式の実体を確認する

金額に関わるセルは、表示値ではなく**数式の実体**を読む。

```bash
gog sheets get <id> "'機能一覧（正規化）'!O36:T43" --render FORMULA --json --results-only
```

`人日単価 ¥10,000` というラベルのセルが、数式では `=S39*8*S41`（8時間を掛けている＝実体は時間単価）だった事故が実際に起きている。ラベルを信じない。

あわせて確認すること:

- 全データ行に数式が入っているか（手入力の数値が混ざっていないか）
- 行の数式に `ROUND` が入っていないか
- 合計行が生の `SUM` から取られているか（丸めた値の連鎖になっていないか）

これらは `scripts/verify_estimate_sheet.py` が自動で検査する。

## 5. Markdown から Google Docs を作る

作業ディレクトリの Markdown を原本とし、そこから Docs を生成する。

新規作成:

```bash
gog docs create "【お見積書兼ご提案書】案件名" \
  --parent=<DriveフォルダID> \
  --file=<原本.md> \
  --json --results-only
```

既存ドキュメントの更新（URL を変えたくない場合）:

```bash
gog docs write <docId> --file=<原本.md> --markdown --replace --force
```

`--markdown` は `--replace` または `--append` と併用が必須。

**Docs を直接編集しない。** Markdown 原本を直して再生成する。直接編集すると次の再生成で消え、原本と乖離する。

### 既存 Docs を更新するとき（上書き事故の防止）

自分は直接編集しなくても、**ユーザーや関係者が Docs を直接微調整していることがある**。差分確認なしの `--replace` はその編集を消す。書き戻す前に必ず:

```bash
gog docs export <docId> --format md --out /tmp/latest.md
```

で最新を取得し、ローカル原本との差分を確認して Docs 側の編集をローカルへ取り込んでから `docs write --replace` する。エクスポートには書式ノイズ（`\#` 等のエスケープ、`<br>` の平坦化、`-`→`*` の箇条書き記号）が混ざるため、差分は正規化してから比較する。

## 6. gog docs の落とし穴

| 事象 | 対処 |
|---|---|
| ファイル先頭の `---` が frontmatter として解釈されうる | 本文を `# 見出し` から始める。区切り線を先頭に置かない |
| コードブロック（``` 囲み）が1行ずつ別段落になり間延びする | 計算フローなどは**表に置き換える**。客先向け文書にコードブロックは合わない |
| 表のセル内で改行したい | `<br>` が改行として反映される（書誌情報の提出者欄など） |
| 見出しレベル | `#`〜`####` が HEADING_1〜4 に対応する |

Markdown の表はネイティブ表として取り込まれる。表を使うほど読みやすい文書になる。

## 7. 生成後の検証

生成しただけで完了としない。構造が壊れていないかを確認する。

```bash
gog docs tables list <docId> --plain | head -3     # ネイティブ表になっているか
gog docs tables list <docId> --plain | wc -l       # 表の数
gog docs headings list <docId> --plain             # 見出し階層
gog docs cat <docId> | head -30                    # 冒頭の見え方
```

確認項目:

- 表の数が Markdown の表の数と一致するか
- 見出しが HEADING_1〜4 として認識されているか（プレーンテキストに落ちていないか）
- `<br>` を使った箇所が改行になっているか
- 意図せず残った Markdown 記法（`|` の羅列など）が本文に出ていないか

## 8. 成果物の区分とライフサイクル

ファイルの具体的な配置は**各プロジェクトの規約（CLAUDE.md / AGENTS.md / docs の README 等）に従う**。規約が無ければ既存の構成に合わせ、判断がつかなければユーザーに確認する。本スキルが定めるのは配置ではなく、次の区分とライフサイクルである。

| 区分 | ライフサイクル |
|---|---|
| 一次情報（議事録・クライアント提供資料） | 不可侵。読むだけ。編集・削除・移動しない |
| 中間物（シート更新用ペイロード等） | 使い捨て。`/tmp` に置き、リポジトリに残さない |
| 成果物の原本（見積書等の Markdown） | 恒久。リポジトリで管理し、Docs の再生成に使う |
| 客先提出物（Google Docs） | Drive の指定フォルダ。原本から生成する |

Drive フォルダ ID はユーザーから受け取る。**フォルダを勝手に作らない。** シートと Docs は同じフォルダに置いてよいが、**Docs からシートへリンクしない**（§1 のとおりシートは内部資料）。
